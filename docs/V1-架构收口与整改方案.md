# Review Agent V1 架构收口与整改方案

> **本方案针对：** `Review-Agent_架构审查意见与整改建议.md`（下称《审查意见》）
> **基线：** `VERSION` = 0.9.2，HEAD `ac4e1af`，tag `v0.9.2-arch-v1`
> **性质：** 实施方案（不是评审意见的复述）。每一条都可落到文件、接口、验收命令。
> **阅读顺序：** §1 裁决表 → §2~§4 三条线 → §5 变更汇总 → §6 迁移顺序 → §7 验收命令。

## 0. 一句话结论

《审查意见》的方向（架构收口 / 证据可信度 / 工程闭环）是对的，**但它对代码现状的判断有 5 处已经落后于实现**（工具层协议、Ledger 墓碑、Human Review 槽位、Git tag、`checks` 失败数）、**3 处需要修正**（所谓"证据状态"其实是第二根轴；`RECOVERABLE` 不该是状态；`interfaces/` 是位置不是依赖治理），**并且漏掉了 5 个比它列的更关键的断点**（§1.4：反向索引断链、v1 报告无原文快照、research 缓存落原文、工具审计旁路、交付包含明文密钥）。

如果按原文原样立项，会出现「重做已经存在的东西」和「引入一个会立刻让 100% 报告降级的闸门」。

本方案做三件事：

1. 把意见的 20 条判断逐条钉到代码事实上（§1），消除认知偏差；
2. 把真正缺的 20 个工作项（A1–A4 / B1–B5 / C1–C7 / D1–D4）按「可独立发布 + 可回滚」排成 4 个批次（§2~§6）；
3. 给出每条验收命令与阶段完成标准（§7~§8）。

## 2. A 线：单一执行链路（V1 接管，Legacy 退役）

### 2.1 目标与判据

**目标态：** `review.py` 的 `main()` 只剩参数解析与装配，审查执行只有一条路径（`ReviewApplication`）；`run_one` 只作为回滚开关背后的一段死代码存在一个版本，然后删除。

**切流判据（全部满足才允许把 `DEFAULT_ENGINE` 改为 `v1`）：**

1. `UNSUPPORTED_BLOCKS` 清零（**2026-11-01 已达成**：`law_library` A1、`research` A2）。
2. `--engine shadow` 在真实使用中累计 **≥ 20 个样本**且**连续 7 天**零未解释差异（`state/double_run/*.json` 的 `diff.unexplained == []`）。当前只有 4 个语料的一次性比对（`REFACTOR_PLAN.md:240` 自认未达标）。
3. `python tools/integrity.py verify` 覆盖两条链（`chain.log` + `v1-chain.log`）全绿。
4. server 端不再依赖 `outputs/*.json` 增量判成功（见 C2，否则切了必然误报）。
5. 回滚演练通过：不删数据、只改开关，5 分钟内回到 `legacy`。

### 2.2 为什么不能"直接删 Legacy"

`run_one` 里有三块能力 v1 还没有：法条库引用（`law_library`）、库外状态核验（`research`）、报告渲染管线（`render_md`，`review.py:3795-4132`）。删掉它等于删掉这三块结论。**先搬能力，再删路径** —— 这是本方案唯一的顺序硬约束。

## 3. B 线：证据可信度（把"有引用"升级为"有证据"）

### 3.1 现状：证据只有一根轴

| 轴 | 现状 | 位置 |
| --- | --- | --- |
| 锚定（这句话在不在原文里） | **已实现**：四值 + 逐字校验 + 丢弃不可回查 | `enums.Verification`、`nodes/evidence.py:53-141` |
| 强度（这句话够不够证明这条结论） | **不存在** | —— |
| 双向索引 | **断的**：`finding_ids` 有，`Finding.evidence_ids` 在 v1 恒空（N1） | `models.py:356,395`；`node.py:356-363` |
| 原文可复核 | **弱的**：报告带 `target_text`（旧）/ 只带 `target.hash`（v1，N2） | `review.py:3380`、`shadow_report.py:130-137` |

后果正是《审查意见》举的例子：材料写「营收 100 亿」，quote 校验成功 → `ANCHORED` → 报告算「可回溯」，但外部来源显示 80 亿时，系统没有任何字段能表达「这条证据被反证了」。

**所以整改不是"给证据加状态"，而是给证据加第二根轴，并且让裁定策略读这根轴。**

### 3.2 设计：`EvidenceStrength`（B1）

新增枚举（`domain/enums.py`），**与 `Verification` 正交，不得合并**：

```python
class EvidenceStrength(StrEnum):
    UNASSESSED   = "unassessed"    # 未评估（缺省值，历史报告导入后即此值）
    VERIFIED     = "verified"      # 来源+主体+指标+时间四项均核验，且无相反证据
    PARTIAL      = "partial"       # 只核验了部分（如仅主体匹配、时间口径不明）
    UNVERIFIED   = "unverified"    # 声称有来源但无从核验（无快照/无域名/抓取失败）
    CONTRADICTED = "contradicted"  # 存在相反证据（必须进冲突处理）
```

**为什么不用意见里的四个值直接替换 `Verification`：** 现有 202 份历史报告、`adapters/legacy_report.py` 与 `checks/test_legacy_adapter.py` 全部依赖 `verification` 的四值语义；改语义 = 批量改历史结论，直接违反 ADR-007。

**判定表（两块证据，两套规则，都是确定性的）：**

| 证据类型 | 判 VERIFIED 的条件 | 判 PARTIAL 的条件 | 判 CONTRADICTED 的条件 |
| --- | --- | --- | --- |
| `QUOTE`（原文） | `verification==ANCHORED` 且 `location.char_start` 非空 | `ANCHORED` 但 `char_start` 缺失（只能靠子串搜到） | 同一 `location` 上有 `Dispute(kind=CONTRADICTION)` |
| `EXTERNAL_SOURCE` | `source.official==True` 且四项匹配全 `True` 且 `contra==[]` | 四项匹配 ≥2 项为 `True`，或无官方域但 ≥2 独立域名一致 | `contra` 非空（`tools/research.py:883-898` 已能给出） |
| `RULE_REFERENCE` | 规则 id 存在于当前 `ruleset` 且未被 scenario 关闭 | 规则存在但被 scenario 关闭 | —— |
| `KNOWLEDGE_ENTRY` / `TOOL_OUTPUT` | 首次出现即 `UNVERIFIED`（设计如此） | —— | —— |

**四项匹配**（新增值对象，`domain/models.py`）：

```python
@dataclass(frozen=True, slots=True)
class MatchCheck:
    kind: str            # source_identity | subject | metric | period
    ok: bool | None      # None = 无法判定（不得当作通过）
    detail: str = ""

@dataclass(frozen=True, slots=True)
class EvidenceAssessment:
    checks: tuple[MatchCheck, ...] = ()
    assessed_by: str = ""        # 工具名，进审计
    assessed_at: datetime | None = None
```

**`Evidence` 新增字段（全部带默认值 → 历史 JSON 原样可读）：**

```python
strength: EvidenceStrength = EvidenceStrength.UNASSESSED
assessment: EvidenceAssessment | None = None
contradicted_by: tuple[str, ...] = ()   # 相反证据的 evidence_id
source: SourceRef | None = None          # 外部来源元数据（今天 source_ref 从未被填过）

@dataclass(frozen=True, slots=True)
class SourceRef:
    url: str
    domain: str
    official: bool = False          # 对应 research 的 official_domains 白名单
    fetched_at: datetime | None = None
    snapshot_hash: str | None = None  # 抓取正文的 sha256，用于"半年后还能复核"
```

**新增硬不变量（构造即校验）：**

- `strength is VERIFIED` ⇒ `assessed_by` 非空 **且** `assessment.checks` 覆盖四项 **且** 全部 `ok is True`；
- `strength is CONTRADICTED` ⇒ `contradicted_by` 非空；
- `strength is UNASSESSED` ⇒ `assessment is None`（不许"评估了但没结论"）；
- `kind is EXTERNAL_SOURCE` ⇒ `source is not None`；且**要标 `VERIFIED` 就必须有正文快照**（`source.snapshot_hash` 非空）——
  没有快照的外部来源只能到 `PARTIAL`（落地写法见 §6「批次 3 进展」的解释性收窄）。

> 这三条不变量是这轮整改的核心：**它让"强度"无法被随手写成 VERIFIED**。模型输出不参与强度判定（遵守 ADR-003）。

**同时补两个已发现的断点（都在 B1 范围内，否则后面的图与闸门都建在沙子上）：**

1. **双向索引补齐（N1）：** `advance()` 增加 `finding.evidence_ids ⊆ state.evidence` 校验，`EvidenceAssessorNode` 写证据时同步回填 `Finding.evidence_ids`（Finding 不可变 → 走 `NodeResult.revisions`，`cross_review.py:119` 已有先例）。
2. **原文快照（N2）：** v1 报告 `target` 块增加 `snapshot_ref`（`state/text/<sha256>.txt`）+ `snapshot_hash`，并保留 `target_text` 键（与旧报告同形，`review.py:3380`）。**没有它，报告无法自证 quote 在原文里，"允许别人独立验证"就是一句口号。**

### 3.3 评估节点：加在已有阶段内，不动状态机（B2）

不新增阶段（`Stage` 与 `STAGE_ARTIFACTS` 是冻结契约，`transitions.py:69-78`）。编排器已支持「一阶段多节点」（`orchestrator.py:226-250`），所以：

- 新增 `review_agent/runtime/nodes/evidence_assess.py::EvidenceAssessorNode`（`stage=EVIDENCE`，`produces={"evidence"}`）。
- `application/service.py:74-86` 的 `workflow()` 在 `EvidenceAnalyzerNode` 之后插入它。
- `STAGE_ARTIFACTS[EVIDENCE]` 不变（仍是 `evidence` / `evidence_dropped`）。

**顺序不可颠倒的两条：**

1. **评估节点必须先于闸门（§3.4）上线**。否则所有证据都是 `UNASSESSED`，闸门一开，100% 报告降级为 `warn` —— 这是最容易犯的错。
2. **评估必须先于 `CrossReview`**。跨节点要读强度判"充分性"，读反了就是拿未评估的证据做冲突判定。

### 3.4 证据闸门（`EvidenceGate`）：让强度真的改变裁定（B3）

新增纯函数（`domain/policy.py`），与 `DecisionPolicy.decide_from_counts` 并列，**默认不启用**：

```python
@dataclass(frozen=True, slots=True)
class EvidenceGate:
    cap: Verdict          # 允许的最高裁定
    capped: tuple[str, ...]   # 被压制的 finding id
    reasons: tuple[str, ...]
    needs_human: bool

def evidence_gate(findings, evidence, *, enabled: bool = False) -> EvidenceGate: ...
```

规则（每条都写进 docstring 并逐条测试）：

| 规则 | 内容 | 理由 |
| --- | --- | --- |
| G1 | 一条 finding 的支撑强度 = 其所有证据强度的**最弱一环**（序 `UNASSESSED < UNVERIFIED < PARTIAL < VERIFIED`） | 三份弱证据不构成一份强证据 |
| G2 | `blocker`/`major` 的支撑强度 ∈ {`UNASSESSED`,`UNVERIFIED`} → 该 finding **不计入 fail 判定**，`cap = WARN`，`needs_human = True` | 「未验证的证据不得支撑确定性结论」 |
| G3 | 任一支撑证据为 `CONTRADICTED` → 生成 `Dispute(kind=CONTRADICTION)`（`DisputeKind` 已有该值），全局 `cap = WARN` | 冲突必须进争议队列，不能靠降权了事 |
| G4 | 支撑强度 = `PARTIAL` → `cap = WARN`，finding 保留原严重度但报告 `limitations` 记「部分核验」 | 「PARTIAL 必须限制结论强度」 |
| G5 | `enabled=False`（缺省）→ `cap=PASS`、`capped=()`，即**完全等价于今天的裁定** | 保证 202 份历史报告重放零差异 |

启用方式：`DecisionPolicy(evidence_gate_enabled=True)`；策略版本升 `"2"`（`policy.py:58` 的 `version` 字段是既定的口径版本位）。

**验收（`checks/test_evidence_gate.py`，新）**

1. `enabled=False` 时，全量历史报告重放：`consistency_issues` 与今天**逐份相同**（当前 5 份已登记偏差不变）。
2. blocker + `UNVERIFIED` → `verdict == warn`、`requires_human_review is True`、`reasons` 含「证据强度不足」。
3. `CONTRADICTED` → `disputes` 出现 `kind=contradiction`，且 `decision.rule_refs` 为空（fail 不成立）。
4. 同一输入跑两次 → `state_hash` 相同（闸门必须纯函数）。

## 4. C 线：工程闭环（任务 / 台账 / 数据）

### 4.1 任务生命周期（C1）

**采纳：** 增加 `QUEUED`、`CANCELLED`。
**不采纳 `RECOVERABLE`：** "可恢复"是**判断**不是**状态**。加进状态机后会出现"记录说可恢复但 checkpoint 已被清理"的两套真相。改为推导函数：

```python
# domain/transitions.py
def recoverable(status: RunStatus, has_checkpoint: bool, has_live_executor: bool) -> bool:
    return status is RunStatus.RUNNING and has_checkpoint and not has_live_executor
```

**状态机变更（`transitions.py:27-39`）：**

```
CREATED → QUEUED → RUNNING → COMPLETED | FAILED | ABORTED
                     ↓
                  CANCELLED        （QUEUED 亦可直接 → CANCELLED）
```

`ABORTED` 保留给"进程级中断"（与 `CANCELLED` 区分：前者是系统原因，后者是用户原因，报告的 `limitations` 措辞不同）。

**取消必须做在阶段边界，不是强杀：**

- 新增 `review_agent/runtime/cancel.py`：`CancellationToken`（`threading.Event` 包装，提供 `cancelled` / `raise_if_cancelled()`）。
- `Orchestrator.run(state, *, token=None)`：每个阶段开始（`orchestrator.py:224` 循环体首行）与每个节点开始（`:236`）前检查；命中则返回 `RunOutcome(status=ABORTED, errors=("已取消",))`，**不落半份报告**（报告只在 FINALIZE 写）。
- 为什么不在 `asyncio.wait_for` 里强杀：节点大多是同步纯计算（`/` 与 SQLite 之外无 IO），强杀会留下半写的 `state/runs/*.state.json`；阶段边界是已有的原子点（`orchestrator.py:251` 落检查点）。

### 4.2 server 与 TaskService 整合（C2）

现状是**双轨且互不相连**：`server.py` 全文搜不到 `review_agent` / `TaskService` / `engine`；`JOBS` 是纯内存字典（`:100-101`）；任务记录目录 `state/tasks/` **实测不存在** —— 任务身份从未在生产落盘。`TaskService` 只在 `review.py:4562-4568` 被装配，除测试外无调用点。

**目标：一条真相 = `state/tasks/<review_id>.json`。** `JOBS` 退化为"读时投影"，只保留给老前端。

- **进程内执行：** `_run_review_job` 改为调用 `review.make_task_service(...).start_async(target, ...)`；`logs/.jobs/<job>.jsonl` 仍写（前端兼容，`server.py:1436-1448` 读它），但内容由 `TaskRecord` 变更事件投影。
- **为什么必须进程内（这是意见没说的依赖链）：** 子进程无法取消（杀进程 = 丢半份状态），也无法把 `RunState` 的 checkpoint 交回任务层。**C1 的取消能力倒逼 C2**，而 C2 又是 A 线切引擎的前置（判成功口径）。三者顺序不能反。
- **判成功改口径：** 不再看 `outputs/` 增量，改看 `TaskRecord.status`；`report_path` 由 runner 返回（`_write_shadow_report` 已返回路径，`review.py:4543-4550`）。**这条是 A3/切引擎的前置**，否则 v1 必然误报（§1.1 第 1 行）。
- **报告归属不能再用目录差集：** 现在靠 `before/after` 快照认领新报告（`server.py:2238+2286-2293`），**两个并发任务会认领到对方的报告**。改用 `TaskRecord.report_path` 后此问题自然消失。
- **幂等键：** `TaskService.start_review(..., idempotency_key=sha256(target_hash|profile_id|purpose_hash|engine))`；同键且状态 ∈ {QUEUED, RUNNING} → 直接返回已有 `review_id`。实测依据：`ledger/chain.log` 286 行只有 **77 个不同 `target_hash`**，同一份材料最多被审 **15 次**（15 个 review_id、15 份报告）—— 这就是零幂等的代价。
- **恢复不缺参数：** 旧恢复流程把 `llm/research/type/agent/scenario/format_spec` 一律置 `None`（`server.py:2175-2180`），无法按原参数重跑；而 `TaskRecord` 已带 `engine / profile_id / purpose`（`tasks.py:88-97`）—— 接上即可补这个洞，不用新字段。
- **并发闸门要落盘：** 现在"同一时间只允许一个审查"是内存判断（`server.py:1548-1552`），而同步接口不占位（`:1923-1925`）→ 两个子进程可同时写同一份 ledger/outputs。改为基于 `state/tasks` 的租约（lease）判断。
- **回滚：** `--legacy-subprocess` 开关，一键回到今天的执行方式（`JOBS` + 子进程）。

### 4.3 Ledger：从"整文件重写"改为"追加墓碑"（C4）

现状：墓碑语义对（`server.py:1222-1300`），机制错（`:1293-1295`）。三个具体缺陷：

1. **不持锁**：`_mark_ledger_deleted` 整文件读（`:1277`）→ 改 JSON（`:1280-1291`）→ 写 `chain.tmp` → `os.replace` 整文件替换。窗口期内若有审查进程在锁内追加（`review.py:3514-3521`），新行被**静默吞掉**；而 `seq` 用行数推导（`review.py:3508`、`:4461`）→ 后续 `seq` 重复、链断。
2. **临时名固定** `ledger/chain.tmp`（`:1293`）→ 两个并发删除互相覆盖。
3. **无异常处理**：Windows 上 `os.replace` 撞上别人正 append 打开的文件会 `PermissionError`，而 `do_DELETE` 没有 try/except（`server.py:786-802`）→ 连接被掐，用户看到 500 或空响应。

**改法：**

- 新增 `review_agent/infrastructure/ledger.py`：
  - `append(entry)` —— 与现状同格式；
  - `tombstone(target_seq, actor, reason, ts)` —— **追加一行** `{"op":"delete","target_seq":N,...}`，不碰已有行；
  - `verify(path)` —— 支持两种形态：①新式独立墓碑行；②旧式原位 `op=delete` 行（server 已产出的那批），标注 `legacy_tombstone=True`；
  - `ledger_lock()` —— 抽出 `review.py:2323-2373` 的 `O_EXCL` 锁（含 30s 超时、60s 陈旧清理、Windows `PermissionError` 兼容），**`review.py` 与 `server.py` 共用同一把**；
  - 墓碑行用**逐次唯一的临时名**（`chain.<pid>.<uuid>.tmp`）。
- `server.py:_mark_ledger_deleted` 改为调用 `ledger.tombstone(...)`，删掉整文件重写逻辑；`do_DELETE` 包 try/except 返回结构化错误。
- `tools/integrity.py:95-112` 的 `verify_ledger` 增加 `op` 行处理；`/api/integrity`（`server.py:1595-1626`）统计时把墓碑计为 `deleted` 而不是 `missing`。

**验收：** 新增 `checks/test_ledger_concurrency.py`：起 8 个线程并发 `append` × 200 + 4 个线程 `tombstone` × 50，断言 ①行数 = 1600 + 200；②`verify()` 通过；③无重复 `seq`。

### 4.7 工具层：先接线，再补 4 项（C7）

工具协议已经足够（`ToolResult` / `Permission` / `ToolContext` / `ToolInvocation` 全在，见 §1.1 第 6 行）。**但今天有三件事比"补字段"更急：**

**然后才补 4 个执行约束**，全部加在 `ToolRegistry.execute`（`capabilities/tools.py:228-249`）这一处：

| 补什么 | 落点 | 缺省 |
| --- | --- | --- |
| 单工具超时 | `execute(..., timeout=None)` 包 `asyncio.wait_for`（编排器已有同款做法，`orchestrator.py:264-272`） | `None`（不改行为） |
