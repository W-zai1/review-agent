# 知识库自学习：缺口识别 → 权威取证 → 受控晋升

> 姊妹文档：[`自学习闭环.md`](./自学习闭环.md)（规则自学习：学"判定标准"）。
> 本文档讲的是另一条闭环：**学"事实依据"**——让 `facts.json` / `laws/` 从"人工手灌几条"
> 变成"系统发现自己在裸判 → 提醒补依据 → 补完就有据可依"。
>
> 状态：**§8 前两步已实现（v0.8.0）**，本文其余部分是后续迭代的设计依据。
>
> | 阶段 | 状态 | 落在哪 |
> |---|---|---|
> | ① 缺口识别 | **已实现** | `tools/fact_gap.py`（四类缺口 + `state/gap_log.jsonl`） |
> | ② 人工补据 | **已实现** | `fact_gap.py draft` → `tools/fact_promote.py`（门禁/晋升/回滚/审计） |
> | ③ shadow 预演 | **已实现（2026-10-28 修正）** | 在 35 例金标准语料上算 `on_target` / `off_target`，**`off_target` 取增量**（`after − before`），跑**生产同款模式**（rule+llm） |
> | ④ 权威源自动取证 | 未实现 | 刻意不做：联网取证的结论不可重放，见 README §38.2 |
> | ⑤ 多源一致性 | 未实现 | 目前靠 `note` 里写清口径 + 人工核对 |
>
> 实测与边界见 README §39。下面保留原始设计以便对照，与实现有出入处已就地标注。

---

## 1. 它和规则自学习有什么不同

| | 规则自学习（已实现） | 知识库自学习（本文） |
|---|---|---|
| 学什么 | 模式："这种写法要报" | 断言："X 的真实值是 Y" |
| 信号起点 | 人标注误报 / 漏检 | 系统发现"自己在裸判"（下了事实判断但库里无依据） |
| 产物 | `rules/auto_*.yaml` 判定规则 | `knowledge/facts.json` 或 `knowledge/laws/` 里的可引用断言 |
| 失败形态 | 一条宽松正则误报（可回滚、可下线） | 一条假事实污染**未来所有**判断（更难察觉、代价更高） |
| 取证源 | 不需要外部源，从标注归纳 | 必须来自权威第三方源，**绝不能来自被审文档** |

一句话区分：**规则自学习决定"什么算错"，知识库自学习决定"世界是什么样"。**

---

## 2. 为什么需要它

当前事实审的证据现状（红队测试 2026-10-28 实测）：

- `facts.json` 机器可读断言只有个位数条，且集中在单一实体（豆包）。
- 审到库外实体（华为出货量、劳动合同法试用期）时，系统**没有 rule 级依据**，
  只能靠 `LOGIC-004`（模型常识）报 major——这次蒙对了是运气，不是制度。
- 系统在 `limitations` 里自己承认："库外实体只判缺出处，不判真伪，要判真伪请先补 facts.json"。

知识库自学习就是把"补 facts.json"这件事从"靠人想起"变成"系统报缺口"。

---

## 3. 最高原则：被审文档零信任

规则自学习里，"被审文档不能改规则"是红线。知识库自学习里同理且更严：

**被审文档里出现的任何数字、日期、结论，都只是"待审主张"，永远不是"事实"。**

一旦把被审文档的数字当事实存库，等于让对方（或对手）往法官脑子里塞记忆——
文档写"华为 5 亿台"，下次审查就拿这条去当依据判别人。这条比规则投毒更隐蔽。

推论：学习信号 = **缺口 + 权威源取证**，而不是"文档说了什么"。

---

## 4. 数据流：六阶段闭环

```
 审查中模型对某事实下了判断，但 facts.json / laws/ 里没有这条断言
        │  ① 缺口识别
        ▼
   state/gap_log.jsonl        缺口清单：对什么实体下了判断、缺哪类依据、当时靠什么判的
        │  ② 权威源取证
        │     法律 → knowledge/laws/ 切条检索（law_index.py / law_cite.py）
        │     商业/产品事实 → 官方披露、财报、权威库；或人工录入
        │     ⚠ 来源必须是第三方权威源；被审文档本身永不作为来源
        ▼
   state/fact_candidates/<id>.json   候选断言（隔离区，带 content_hash）
        │  ③ 门禁验证（见 §5）
        ▼
   state/shadow/<id>.json     预演：用候选断言重跑历史语料，看新增/修正哪些 issue，不改结论
        │  ④ 晋升审批（fact 维度只走人工，见 §6）
        ▼
   knowledge/facts.json 或 laws/   写入真断言，带 source / 版本 / 写入人 / 复查日
        │  ⑤ 治理：facts.json 变更挂 integrity hash → 历史报告转 stale；
        │     断言带来源与复查日；法条修正/事实过时 → 标记失效或回滚
        ▼
   ⑥ 同类判断下次从"模型常识蒙"升级为"rule 级有据可依"，evidence 字段指向真来源
```

**结构约束（沿用规则自学习的四条根）：**
1. 候选断言在 `state/fact_candidates/`，**不直接进 `facts.json`**——
   否则"有人起草了事实"和"事实库真的改了"会混为一谈，历史报告的 `knowledge_hash` 会被判篡改。
2. 审查过程（`review.py`）**永不写 `facts.json` / `laws/`**。
3. HTTP 面上没有写知识库的能力；写库只存在于 `tools/fact_promote.py`（新工具，唯一入口）。
4. 断言晋升**只增不改不删**：改一条旧断言 = 新增一条带版本的新断言，旧条目标 `superseded`，不原地覆盖。

## 5. 候选断言 Schema 与门禁

候选断言长这样（写入 `state/fact_candidates/<id>.json`）：

```json
{
  "candidate_id": "FACT-CAND-XXXX",
  "entity": "华为",
  "attr": "2024 全球手机出货量",
  "type": "number | date | text",
  "expected": "约 4000 万台量级",
  "tolerance": null,
  "one_sided": true,
  "rule_id": "FACT-001",
  "source_url": "https://...（权威第三方，如 IDC/Canalys 报告页）",
  "source_title": "Canalys 2024 全球手机市场追踪",
  "effective_date": "2025-01-01",
  "review_due": "2026-04-01",
  "note": "量级基线：5 亿台属离谱；含平板/穿戴须排除",
  "exclude_ctx": ["平板", "穿戴", "IoT"],
  "content_hash": "<本体+来源+标注 的 sha256>",
  "status": "proposed | passed | promoted | rejected | rolled_back"
}
```

> **实现口径（v0.8.0，与上图有出入处以这里为准）**：
> - 期望值用 `expected_num` / `expected_unit` 或 `expected: {num, unit}`（人编辑时更好填）；
> - 单侧上限不是 `one_sided: true`，而是 `type: "max"` + `unit_hint`（写在 rules/knowledge 的既有约定）；
> - 新增 `from_gap`（来源缺口）、`entity_confirmed`（实体是否人工确认）、
>   `evidence_quote` + `evidence_is_from_target`（**永远为 true，且不能当来源**）；
> - `content_hash` 未采用：候选 JSON 本身就是被 hash 的对象，`gap_id` 已够做去重键。

门禁指标（在历史语料上重跑，与不带候选对比）：

| 指标 | 含义 | 门槛 |
|---|---|---|
| `source_verifiable` | source_url / 条款号真实可回查 | 必须通过 |
| `multi_source_agree` | ≥2 个独立权威源一致；否则标 `single_source_pending` | 单一源不自动晋升 |
| `no_conflict` | 与现有 facts.json / laws/ 断言不冲突 | 冲突 → 进 disputes，人工裁定 |
| `type_correct` | 单侧/容差口径正确（如试用期必须 `one_sided=max`，不能用对称容差，否则 3 个月会被误报） | 必须通过 |
| `on_target_hits` | 候选断言在历史语料上，该命中的真错误是否找回来了 | 应有正贡献 |
| `off_target` | 候选**新引入**的误报数（`after − before`，逐句对齐） | **增量 = 0**（同规则自学习：误报代价是"人不再看清单"） |
| `off_target_baseline` | 语料里本来就有、与候选无关的误报 | 不拦候选，但必须报出来（金标准集自己的债） |
| `value_from_target` | 期望值与被审文档里的数字重合时，须有独立 `source_quote` 佐证 | 被审对象不能当证据（**数值也算证据**） |
| `entity_confirmed` | 草稿里的实体经人工确认（正则猜的实体不算） | 必须通过 |
| `measurable` | 语料里有没有一份提到该实体 | 没有 → `unmeasured`（没测过 ≠ 通过） |
| `suppressed_others` | 候选让别的规则结论消失的数量 | ≤ 0 |

> `off_target` 比 `on_target` 更严格，这是刻意的：存一条"把对的判错"的事实，比漏一条危害更大。
>
> 2026-10-28 复核发现初版三处错：`off_target` 用了绝对值（没减基线，存量一条误报就把所有候选判死）、
> shadow 跑在 `use_llm=False` 上（测的不是生产行为）、安全线只防 URL 不防数值。
> 现在 `off_target` 是增量且逐句对齐，模式跟随生产，数值抄自被审文档会被拒。

## 6. 审批与配额

| 维度 | 通道 | 理由 |
|---|---|---|
| `fact`（事实断言） | **只能人工**（`--confirm-manual`） | 存错事实会污染未来所有判断，代价最高 |
| 法律类数值（如试用期上限） | 人工 + 来源必须可回查 | 同属 fact，且错了有法律效力误判风险 |

- fact 类晋升**不设自动通道**（区别于规则自学习里 logic/style 可 `--auto`）。
- 每条晋升必须带 `source_url` 与 `review_due`；缺来源的候选一律停在 `proposed`。
- 治理配额：每周人工晋升不限，但仍受门禁与只增不改约束；队列上限防止积压。

## 7. 治理：版本、审计、时效、回滚

写知识库的每个动作都要：
1. 快照当前 `knowledge/` → `state/knowledge_snapshots/<时间>__<版本>/`（只留最近 10 份）；
2. 写入新断言（只增）；
3. 自增 `config/knowledge_version.txt`；
4. 追加一行 `state/fact_log.jsonl`（`op / entity / attr / by / source / 版本前后 / 指标 / 快照`）。

- 版本自增后，历史报告因 `knowledge_hash` 变化转为 `stale`（"当时的依据已变，结论该重审"）。
- **时效**：每条断言带 `review_due`。到期未复核的断言自动降权（仍可引用，但 evidence 标"待复核"），不自动删除。
- **回滚**：`python tools/fact_promote.py rollback FACT-CAND-XXXX --by <name>` → 删断言 + 升版本 + 记账，候选置 `rolled_back`。
- 法条修正/事实过时：新增一条新断言并把旧条目标 `superseded_by`，不原地改旧值。

## 8. 最小起步（别一上来做全自动）

全自动取证、自动爬网页是后面的事。先做最小闭环的前两步，让"缺口可见"：

1. **缺口识别（第一步，最该先做）**：改审查器，凡是 `LOGIC-004`（模型常识）下事实判断、而 facts.json/laws/ 无对应断言时，自动往 `state/gap_log.jsonl` 记一条：
   对什么实体下了判断、当时 quote、当时靠什么判的（model）、缺哪类依据。
   ——现在系统裸判了自己都不知道。
2. **人工补据（第二步）**：攒一批缺口后，人对着 `gap_log.jsonl` 去 laws/ 或 facts.json 补对应断言。
   ——这时"该补什么"不再靠猜，是系统报出来的。

这两步跑完，第一圈闭环就成立了：**系统发现自己不知道 → 提醒补 → 补完有据可依**。
权威源自动取证、多源一致性、shadow 预演都属于第二步之后的增强。

> **实现补充（v0.8.0）**：第一步按 §8 落地时，判定口径从"只看 `LOGIC-004`"扩大到四类
> （`model_judgment` / `law_missing` / `unsourced_claim` / `watchlist_unasserted`）——
> 因为实测里"裸判"不止 LOGIC-004 一种形态：模型在 fact 维度下的任何判断（含 OPEN-* 与
> FACT-002/003）都可能是无据的。第二步之外还多做了一件：`fact_promote.py` 的六道门禁，
> 否则"人工补据"会退化成"手工编辑 facts.json"（不留审计、不升版本、历史报告被判篡改）。

> **实现补充（v0.8.2）：门禁修对之后，旧断言要回测。**
> 门禁只管"新来的能不能进"，管不了"已经进来的可不可验"。`tools/fact_audit.py` 用**摘除法**
> （`库 vs 库 − 本条`）算每条已入库断言的增量贡献，五档结论
> `kept` / `harmful` / `shadowed` / `weak_signal` / `unmeasured`；只读，不改库。
> **不能用 `fact_promote shadow` 回测**：它的算法是 `库 + 候选 vs 库`，两边都是现库，增量恒 0。
> 实测 9 条：6 kept / 2 shadowed / 1 unmeasured / 0 harmful——回测顺带暴露了两个 bug
> （标注 id 跨语料重名导致好断言被算成零贡献；模型自提的 FACT-001 混进事实库的账）。

## 9. 边界与已知风险（不遮掩）

1. **法律事实好搞，商业事实难搞**：法律有全国人大数据库（`laws/` 已搭好切条检索）；
   商业数字（出货量、MAU、营收）来源零散、随时间变化，初期不要自动爬网页。
2. **初期必然半自动**：系统识别缺口 + 提议断言草稿 + **人确认来源与数值**。
   全自动灌假事实是这个功能最大的风险点。
3. **事实有时效**：MAU 会变、法年会改；`review_due` 不是装饰，是防止"今天的依据明年变成错依据"。
4. **宁可漏、不可错**：宁可让一条断言停在"缺出处"，也不要存一条来源不明的事实——
   假事实比漏检隐蔽十倍。
5. **多源一致对商业事实很难**：不同口径（IDC/Canalys/公司自报）数字本就不同，
   这类断言应标 `口径分歧` 交人工，不强行取一。

| 位置 | 作用 | 状态 |

| `state/fact_candidates/` | 候选断言隔离区 | **已实现**（`fact_gap draft` 起草，`fact_promote` 读写） |
| `state/fact_log.jsonl` | 知识库变更审计 | **已实现**（`fact_promote._log`） |
| `state/knowledge_snapshots/` | 晋升前快照（留最近 10 份） | **已实现** |
| `tools/fact_promote.py` | 唯一写 `facts.json`/`laws/` 的入口 | **已实现**（法条仍走 `law_ingest.py`：要切条与条数门禁，不是"一条断言"） |
| `tools/fact_audit.py` | 回测已入库断言（摘除法算增量贡献） | **已实现**（只读；五档结论） |

> 与规则自学习的边界：规则自学习管"判定标准"（`rules/`、`rule_miner.py`、`rule_promote.py`），
> 本文管"事实依据"（`facts.json`/`laws/`、`gap_log`、`fact_promote.py`）。
> 两条闭环共用同一条安全哲学：**候选隔离、状态重算、被审对象零信任、误报零容忍、只增不改。**
