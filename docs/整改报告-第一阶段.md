## 3. ② 任务生命周期收口到 TaskService

### 3.1 改前

- 状态事实源：`state/tasks/*.json`（FileTaskStore）——**已是唯一**。
- 但生命周期语义有两套：
  - `server.py`：自己 `TaskRecord(...)` + `TASKS.save` + `mark_task` + `finish_task` + `recover_tasks` + `Popen` + `communicate(timeout=...)` + `PROCS`。
  - `application/tasks.py::TaskService`：自己的 `_open/_execute/cancel/recover`，生产零调用（只有 `checks/test_task_service.py` 用）。
- `JOBS` 已是视图（`_job_view`），不是第二份状态。

### 3.2 改后

```
ReviewApplication（v1 流水线）
        ^
        | runner(target, review_id=..., token=...)
TaskService（唯一生命周期：创建 / 幂等 / QUEUED→RUNNING / 完成 / 失败 / 取消 / 超时 / 恢复）
        |
        v
server._SubprocessRunner  ──►  subprocess.Popen(review.py …)  ──►  outputs/ + ledger/
        |
        └── JOBS（仅前端视图）、PROCS（进程句柄）
```

- `TaskService` 新增 `start_review_with(runner, ...)` / `start_async_with(runner, ...)`；现有 `start_review` / `start_async` 签名与行为不变（内部委托）。
- `server._SubprocessRunner` 实现 `Runner` 协议：把「这一次怎么跑」（research / type / scenario / 格式要求 / purpose / 进度文件）封在 runner 里，**进程隔离保留**。
- `_watch_cancel`：TaskService 置位令牌后 `terminate`，10 秒不退再 `kill`；超时与取消共用同一个令牌，不存在第二个超时实现。
- `_run_review_job` 只起进程、盯令牌、返回 `TaskOutcome`；**不再写任务记录**。
- `_start_review`（异步）与 `/api/review`（同步兼容口）都走 `TaskService`；`_cancel_review` 走 `TaskService.cancel`；`_recover_jobs` 走 `TaskService.recover`。
- `server.py` 中 `finish_task` / `mark_task` / `recover_tasks` 的引用数：**0**。

### 3.3 迁移路径与退出条件

- 迁移路径：`server` 只保留「参数校验 + 闸门 + 视图」，执行由 Runner 适配；后续若换成进程内执行，只替换 Runner 实现，TaskService 与路由不动。
- 第二套状态：**不存在**。`JOBS` 只读任务记录生成视图，进程重启后以 `state/tasks/` 为准；已通过 `_recover_jobs` 验证。
- legacy 退出条件（未到，不在本轮执行）：`--engine shadow` 累计 ≥ 20 个真实样本、连续 7 天零未解释差异 + 两条 ledger 校验全绿 + 回滚演练通过；之后才允许删除 `run_one` 运行入口。

### 3.4 CLI 接入 TaskService（第一阶段第 5 条）

- **改前**：手工 `review.py` 走 `_run_v1` 直跑，不建任务记录；只有 Web 走 TaskService。任务层只覆盖 Web。
- **改后**：
  - CLI 默认 v1 → `TaskService.start_review`，任务记录落 `state/tasks/`，与 Web 共用创建/完成/失败语义。
  - server 子进程（`--review-id`）仍走 `_run_v1` 直跑：父进程已持有任务记录，子进程不再建第二条（避免覆盖幂等键/创建时间）。
  - `_run_v1` 拆成 `_run_v1_core`（不打印/不退出）+ `_print_v1_result` + `_run_v1`；两条 CLI 入口共用同一段执行、进度、报告与 `REVIEW_RESULT` 契约。
- **验收（临时副本）**：连续两次手工运行各新增 1 条 `completed/finalize` 任务记录；`--review-id R-20261103-999` 直跑不新增记录（仍 2 条），报告 ID 与给定号一致；`checks` 829 OK、`tests` 686 OK。
- **回滚**：还原 `review.py` 即回到“CLI 不建任务”的旧行为；server 路径不受影响。

## 4.5 P0 复审补记（2026-11-03）

复审时发现两处“看起来已经统一、实际仍可能分叉”的缺口，已修复：

1. **子进程引擎未钉死**：`server._run_review_job` 原来不传 `--engine`，子进程继承宿主环境；若设了 `REVIEW_ENGINE=legacy`，任务记录写 `v1`、实际跑 legacy。现在命令行显式传任务记录的 engine（server 恒 v1）。
2. **状态视图可能压过记录**：`/api/review/status` 只读 `JOBS`；重启后 `JOBS` 可能来自 `.jobs/*.jsonl`，与 `state/tasks` 不一致。现在返回前用任务记录覆盖 `JOBS` 视图，状态/错误/报告以记录为准。

验证：设 `REVIEW_ENGINE=legacy` 起 server → 任务记录 `engine=v1`、报告 `engine=architecture-v1`；CLI 与 server 的 v1 报告顶层键集合一致（35 键，无差异）；新增 `StatusSourceTests` 覆盖“记录优先”。

## 6. 剩余与需决策

1. **（本轮已完成）第一阶段第 5 条「统一 CLI、Web 的审查入口」**：CLI 默认 v1 已接 `TaskService`，与 Web 共用任务创建/完成/失败语义；server 子进程（`--review-id`）按父进程任务记录执行，不重复建任务。legacy / shadow 仍直跑，属于回滚与比对路径。
2. **legacy 删除未做**（按约束不做）：需要 20 样本/7 天后另行书面确认。
3. **同步接口错误分类**：改为读 `TaskService` 记录的 `error` 后再解析 `REVIEW_ERROR`，理论上有信息损失（原实现从子进程 stderr 原始文本解析）。本轮未发现测试依赖；如前端有依赖需单独立项。
4. **超时链路未做端到端实测**：`--review-timeout` 下限 30s（`REVIEW_TIMEOUT_MIN`），单元测试覆盖了「令牌→terminate→FAILED」，但未跑 30s 级真实超时。建议下一轮用长语料补一次。
5. **`tools/release_check.py` 未在本轮运行**：它要求工作区干净（无未暂存/未跟踪文件），而本轮按约定不 `git add` / commit，工作区含未提交改动；因此改用 `secret_scan` + `git archive` 语义说明。等改动提交后（由你决定）再跑：
