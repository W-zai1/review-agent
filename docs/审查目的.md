# 审查目的：一句话 → 审查目标 → 原文证据

> 代码：`tools/purpose.py`　词典：`config/purpose.yaml`　入口：审查台「审查目的」输入框 / 上传目的文件 / `--purpose` / `POST /api/review/start{...,purpose,purpose_files}`

---

## 1. 要解决的问题

用户手里有一份文本，心里有一个目的：

> "这是给客户的报价邮件，帮我找有没有**承诺过头**的地方。"

传统做法是把这句话塞进 prompt 交给模型，然后得到一段"看起来像在回答"的话。
问题有三个，任何一个都足以让结论不能用：

| 问题 | 表现 | 后果 |
|---|---|---|
| **不可复现** | 同一句话问两次，派生出不同目标 | 报告无法复核，也没法和历史对比 |
| **引用幻觉** | 模型"引用"了一句原文，但原文里没有 | 你要自己回原文核，等于没省事 |
| **沉默即通过** | 没找到证据时只输出一段空话 | 你会以为"这个目的没问题"，其实只是没找 |

所以这一步被拆成三层，**只有最后一层允许用模型**：

```
目的文本 ──parse()──▶ 意图 + 目的词 + 目标（确定性，词典驱动）
          ──analyze()─▶ 证据[]（确定性：规则命中 / 目标探针 / 关键词定位，逐字 quote）
          ──judge()──▶ relation + rationale（可选，模型；只能改判定，不能改 quote）
```

---

## 2. 三层各自的职责

### 2.1 解析（`parse`）：一句话 → 目标

- 目的文本按 `config/purpose.yaml` 的 `keywords` 匹配**意图**；取**命中数最高的那一档**，
  同分的全部保留，低于最高分的算弱命中、不带（"找承诺过头"不该顺带列出"口语化"）。
- **泛词不能单独激活意图**（`weak_keywords`）。"交付""数据""来源""客户"这类词
  在长文档里到处都是：一份招聘 JD 只因出现「持续交付」「数据整理」就被判成
  「承诺与交付风险」+「数据与口径」，派生出 4 个与"要不要录用"毫无关系的目标，
  全部 `not_found`。口径是：有非泛词命中 → 有效；只有泛词 → 至少 2 个不同泛词才算数。
- 每个意图带 `goals`，每个 goal 有一句人可读的 `question` 与若干 `probes`（正则）。
  **可以没有 probes**：覆盖面、证据强度、差距陈述这类语义判断，正则写不出可靠口径，
  写了要么打不中、要么命中满篇。这类目标交给 2.4 的语义命中。
- 同时抽取**目的词**：中文二元组，过滤元话语（"帮我/有没有/这是"）与含虚字的跨词组合。
  词表**有上限**（`MAX_TERMS = 24`）：目的文件可到 2000 字，二元组能抽到 300+ 个
  （实测一份招聘 JD 截图 OCR 出 317 个），而定位门槛是"一句命中 ≥2 个词"——
  词表一大，几乎每句都能凑够两个，无关句会把目标命中的证据挤出 `MAX_TERM_EVIDENCE`。
  排序按「词典词 > 该目的内出现次数 > 首次出现位置」，OCR 乱码（只出现一次）自然沉底被截掉。

### 2.2 定位（`analyze`）：目标 → 证据

三类来源，按可信度排序：

| source | 含义 | 可信度 | 说明 |
|---|---|---|---|
| `rule` | 命中该意图指定的规则 | 0.9 | 已由确定性规则判定，只是把它挂到目的上 |
| `goal` | 目标探针命中 | 0.75 | **只定位，不判定**：命中不等于有问题 |
| `dimension` | 属于该意图关注的维度 | 0.55 | 顺带看看，**限量 3 条**，不能挤掉目标证据 |
| `term` | 命中目的关键词 | 0.3–0.7 | 目的里写了具体对象时最有效；**不带目标归属** |

去重按"同一句只留一条"，但**同一句可以同时服务多个目标**：
"我司承诺 15 日内交付，质量绝对没问题" 同时满足"绝对化承诺"和"时间点"两个目标，
丢掉一个就会让目标误报 `not_found`——等于告诉用户"这句话没被考察过"。

### 2.3 裁决（`judge`）：模型判关系，也判目标命中

模型收到的输入是**已经定位好的证据清单**，输出是两段（一次调用）：

```json
{"verdicts":[{"id":"E2","relation":"risk","rationale":"承诺 15 日交付但未给前置条件"}],
 "goals":[{"id":"payment_terms","status":"found","evidence_ids":["E2"],
           "rationale":"写明了账期与含税口径"}]}
```

- `relation` 只能是 `risk / support / insufficient / related`，其它值整条丢弃；
- `status` 只能是 `found / not_found`，`evidence_ids` 只保留字符串编号；
- **不返回 quote**，因此"引用原文"这件事天然不会幻觉；编号对不上就丢弃；
- 兼容旧格式：只给裸数组（`[{...}]`）时按"只有证据关系"处理；
- 调用失败 → `judge.mode` 回落为 `rule`，确定性证据一个不丢，目标状态退回前两层判定。

### 2.4 目标命中：谁说了算（`decided_by`）

这是最容易做错的一层。**只靠规则与探针判 `found`/`not_found` 是不够的**：
探针是正则，覆盖"长什么样"（百分比、日期、金额），覆盖不到
"这句话有没有回应『这个人符合岗位吗』"。语义上明明被回应的目标会一律 `not_found`，
用户看到的就是"系统没有目标命中意识"。

现在目标状态由三者取并集，且每条命中都必须挂在**本轮真实存在**的证据编号上：

| `decided_by` | 判定者 | 报告里的标记 |
|---|---|---|
| `rule` | 命中该目标声明的规则 | ✅ 找到 |
| `probe` | 目标探针命中 | ✅ 找到 |
| `judge` | 模型判定原文回应了该目标 | ✅ 语义命中（唯一来源时） |

两条硬约束：

1. 模型说 `found` 但给出的编号不在本轮证据里 → **按 `not_found` 处理**，
   并在 `note` 里写明"未给出可定位的证据编号"。空口命中不算命中。
2. 模型给的理由（`rationale`）写进 `goal.note`，报告表格下方单独列出。
   只给"命中"不给理由，读者无法判断命中的对不对。

## 3. 报告长什么样

```json
"purpose": {
  "text": "这是给客户的报价邮件，帮我找有没有承诺过头的地方",
  "lexicon_version": "v1-2026-10-25-a2",
  "intents": [{"id":"commitment","name":"承诺与交付风险","rules":["LOGIC-008","LOGIC-006"],
               "matched_keywords":["承诺","承诺过头"]}],
  "goals": [
    {"id":"unfalsifiable_promise","status":"found","evidence_ids":["E1"]},
    {"id":"deadline_promise","status":"not_found","evidence_ids":[]}
  ],
  "evidence": [
    {"id":"E1","quote":"我司承诺本项目在 15 个工作日内完成交付，质量绝对没有问题…",
     "start":42,"relation":"risk","source":"rule","rule_id":"LOGIC-008","relevance":0.9}
  ],
  "judge": {"mode":"rule+llm","calls":1,"judged":1,"unjudged":0},
  "limitations": ["1 个目标在原文中未找到对应表述：…未找到不等于不存在…"]
}
```

报告里的 `purpose` 与 `issues` 是**两件不同的事**：

- `issues` 回答"哪里错了"（全维度，按规则判定）；
- `purpose` 回答"按你的目的，看到了什么"（聚焦，含"没找到"）。

**目的不改变 verdict**。它不提高也不降低严重度——否则"换个说法问"就能改变结论。

## 4. 怎么改词典（`config/purpose.yaml`）

新增一类审查方向：

```yaml
intents:
  - id: my_intent
    name: 我的审查方向
    keywords: [关键词1, 关键词2]        # 目的里出现这些词就激活
    dimensions: [logic]                # 该方向关注的维度
    rules: [LOGIC-001]                 # 该方向指定的规则
    goals:
      - id: my_goal
        rules: [LOGIC-001]             # 目标级归属（优先于意图级）
        question: 人类可读的判定问题
        probes:
          - pattern: "(正则)"
            relation: risk             # risk / support
```

三条纪律：

1. **改词典必须同步 `version` 字段**（`v1-2026-10-25` 这种格式）。
   报告里记了 `purpose.lexicon_version`，版本没变而内容变了，
   就等于"同一句目的昨天派生出两个目标、今天派生出一个"，无法解释。
2. **探针只定位、不判定**。`relation` 写 `risk` 只表示"这句话是风险类信号"，
   真正下结论要靠规则命中或模型裁决。
3. **每类探针命中上限是 3**（`PER_GOAL_HITS`）。探针写宽了会刷出一屏"相关句"，
   把真正的证据挤下去——这是前几轮"误报放大器"教训的直接应用。

## 5. 已知边界

| 边界 | 现状 | 影响 |
|---|---|---|
| 关键词法理解目的 | 目的是"别让法务挑出毛病"这类抽象说法时，匹配不到意图 | 会退化成"只按关键词定位"，并显式写出这条限制 |
| 二元组噪声 | 不引入分词器，"份合"这类跨词二元组会残留 | 无害：它几乎不会在原文命中 |
| 探针宽泛 | "付款"这类词在一份合同里会出现几十次 | 已按每目标 3 条硬限 |
| 中文为主 | 目的与探针都是中文正则 | 英文目的基本只能靠关键词命中 |
| 未找到 ≠ 不存在 | 只代表规则与探针没定位到 | 报告在 `goals` 与 `limitations` 双处写明 |
| 否定式目的无效 | "不要检查承诺" 仍会命中 commitment：关键词是子串匹配，没有否定语义 | 目前只能靠人把目的写成正向（"只核对金额"） |
| 繁体 | "承諾十五個工作日" 不匹配简体探针 | 中文为主可接受；加繁体词表属另一件事 |
| 引用无法定位即剔除 | 规则给的 quote 与原文有细微差异（空格/全角）时，证据会被排除并写进 limitations | 绝不写伪偏移；这些结论仍在 issues 清单里 |

## 6. 三种用法

```bash
# CLI
python review.py targets/contract_001.md --no-llm \
  --purpose "帮我核对合同金额、大小写与付款条款是否一致"
```

```javascript
// 控制台：审查台左栏「审查目的」输入框（存 localStorage，随审查一起提交）
POST /api/review/start {"file":"targets/contract_001.md","llm":false,
                        "purpose":"找没有标注来源的数据"}
```

```javascript
// 控制台：目的也可以来自文件（审查要求 / 检查清单 / 客户邮件…）
// 入口与「待审对象上传」同形态：整块虚线区可点选、可拖放、可一次多选；
// 多选时前端**串行**上传，理由见 6.2。
// ① 上传：摄取成文本后暂存 state/purpose_uploads/，返回附件条
POST /api/purpose/upload?name=审查要求.pdf   （裸字节，与 /api/upload 同一协议）
// ② 运行审查时只传 id；服务端把手写目的 + 文件文本组装成一段目的
POST /api/review/start {"file":"…","llm":false,
                        "purpose":"帮我核对合同金额",          // 可省略
                        "purpose_files":["a1b2c3d4e5f6"]}      // ≤5 个
```

结论条目上的「定位原文 ›」会在原文标注区闪一下对应片段——
用 `Range.getBoundingClientRect()` 取位置后盖一层临时高亮，1.8 秒淡出。

## 6.1 目的文件：上限与截断（为什么不是"想传多少传多少"）

目的文本不是只存进报告就完了——它会经 `charter_block()` 注入**每个维度**的 prompt，
长文还要分块调用。所以文件类目的上限是**分层显式**的，没有一层是静默的：

| 层 | 上限 | 截断后怎么让人知道 |
|---|---|---|
| 单份目的文件 | 2000 字（`PURPOSE_FILE_MAX`） | 上传响应 `truncated:true` + warning；附件条显示「已截断」 |
| 组装总文本 | 6000 字（`PURPOSE_TOTAL_MAX`） | 截断说明**并进目的文本**，报告 `purpose.text` 原样展示 |
| `parse()` 解析 | 由 `--purpose-max` 显式传入（手写默认 300） | `purpose.limitations`：「目的文本超过 N 字，已截断到前 N 字解析」 |

手写输入保持 300 字不变（`purpose.parse()` 的默认预算）；只有带目的文件时，
服务端才把实际上限经 `--purpose-max` 传给子进程。**全局上限没有被动过**——
否则"换个说法问"或"多传一个文件"就会静默改变审查行为。

其它约束：一次最多 5 个目的文件；暂存区容量 20 个（只传不删会攒爆磁盘，删了才能传）；
目的文件暂存在 `state/purpose_uploads/`，**不是** `targets/`——它们是说明材料，
不会出现在待审列表里；提取不到文本的文件（扫描件、无 OCR 时的图片）直接拒绝，
不留一个空目的文件等着被静默忽略。

## 6.2 前端多选为什么是串行上传

目的文件上传接口的判定顺序是「读现有列表 → 判是否满 5 个 → 落盘」。

并发上传会让 N 个请求**同时**读到同一个「未满」状态，各自判定通过后一起落盘——
5 个的上限在批量选择面前就形同虚设。所以前端 `addPurposeFiles()` 用一个队列
串行消费（`purposeBusy` 单 worker），并且**每个文件上传前重新判一次上限**：
批量选择的超量部分在入口拦一次、循环里再兜一次。

代价是批量上传总耗时是线性的；收益是上限与报告里的「目的文件 N 个」始终一致。
上传期间虚线区 `disabled`、状态行显示「正在上传 i/n：文件名」，用户不会误以为卡死。

## 6.3 目的文件是图片时，OCR 风险必须进报告

待审对象是图片时，报告一直有 OCR 提示（`source_meta.kind == "image"`）；
但**目的文件**是图片时没有——而目的文件是**判定标准**，认错一个字改的是标准本身。

实测：一份招聘 JD 截图 OCR 出「霭霭幕法岗」「催理加速」「勺苜排」，
报告照样给出「学历未提及 / 关键项未覆盖」，limitations 里一个字都没提。
上传时那条 warning 只是 `toast` 一闪，用户事后翻报告根本看不到。

现在的链路：

```
/api/purpose/upload  → record.kind == "image"（warnings 里也有识别误差提示）
_assemble_purpose()  → 第三个返回值 quality[]（**不进目的正文**，正文会被当要求侧）
--purpose-notes JSON → review.run_one(purpose_notes=[...])
报告 limitations     → 插在**最前面**
```

三个要点：

1. **不进正文**：目的正文会被 `match_matrix.blocks` 当作「要求侧」逐条对照，
   塞一条元信息进去会污染矩阵；
2. **不做成 `（说明：…）` 尾巴**：那段是截断/改名的机器说明，位置在正文末尾，
   读报告的人（和解析器）都不会把它当结论前提；
3. **排最前**：判定标准存疑时，后面「覆盖了多少条规则」的说法都不该先被读到。

没有目的时（`purpose=None`）这条提示不出现——不能凭空给一份普通文本加一句
「目的文件…」，那会让人以为系统搞错了对象。

## 7. 测试锁了什么

`tests/test_purpose.py`（40 项）+ `tests/test_api_contract.py::PurposeApiTests`（4 项）
+ `tests/test_api_contract.py::PurposeUploadTests`（12 项）：

- 解析确定性（同输入 → 同输出，逐字节）；
- 目的词的噪声过滤边界；
- 证据 quote **必须逐字出现在原文**；
- 一句话服务两个目标时不被去重吃掉；
- 模型返回非法 `relation` / 未知 id / 伪造 quote 时，**一律丢弃且不改原文引用**；
- 模型调用失败时降级而不是丢证据；
- 报告与 markdown 都出现目的块，任务日志有 `S5.5` 步骤；
- API 层：目的透传、300 字截断、不填目的时 `purpose: null`；
- 目的文件：txt/pdf/docx/zip 摄取暂存、2000 字截断告警、**不进待审列表**、
  无文本图片明确拒绝、暂存容量上限、删除含路径穿越防护、
  随审查进报告（手写 + 文件组装、意图被文件内容激活）、
  启动前拒绝坏 id 与超量、`max_chars` 抬高解析预算且截断提示用实际上限；
- 前端契约：目的文件区与待审上传同形态（虚线区 + `multiple` 多选 + 拖放绑在虚线区
  且 `stopPropagation` 防面板二次消费）、报告侧标出目的来源与「【目的文件：x】」段落。

**要求侧与候选侧逐项对照**（学历 / 年限 / 技能 / 薪资 / 到岗）另有一层，见
`docs/要求对照矩阵.md`：那一层不进 `evidence`，只回答"要求逐项对上了没有"。
