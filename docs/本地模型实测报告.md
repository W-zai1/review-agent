## 三、核心发现：思考型模型的 "token 饥饿"

Ollama 把思考链放在 `message.reasoning`（**不是** `reasoning_content`），`message.content` 才是最终正文。
思考链先于正文生成，**预算不够时正文恒为空**：

| max_tokens | content 长度 | reasoning 长度 | finish_reason | 结论 |
|---|---|---|---|---|
| 8 | 0 | 9 | `length` | 思考都没写完 |
| 64 | 0 | 98 | `length` | 同上 |
| 256 | 0 | 409 | `length` | 思考链几乎写满 |
| 1024 | **3** | 525 | `stop` | ✅ 出现正文 |
| 2048 | **3** | 525 | `stop` | ✅ |

**阈值结论：思考链约需 525 token，`max_tokens` 必须 ≥ 1024 才有正文。**

### 由此暴露的产品 Bug（已修）

`server.py` 的 `/api/llm/test` 硬编码了 `max_tokens=8`、并把超时压到 20s：

```python
# 修复前
cfg = replace(base, enabled=True, timeout=min(float(base.timeout or 40), 20), max_retries=0)
res = client.chat([{"role": "user", "content": "ping"}], temperature=0, max_tokens=8)
```

对普通模型 8 token 够回 "pong"；对**思考型模型**必然得到空正文。
用户在控制台点「测试连接」看到的是 **"连接成功，但回复是空白"**——误以为配置错了。

**修复后**（`server.py:736-777`）：

```python
cfg = replace(base, enabled=True, timeout=min(float(base.timeout or 40), 60), max_retries=0)
res = client.chat([{"role": "user", "content": "只回复两个字：可用"}], temperature=0, max_tokens=256)
# reply 为空时额外返回 note 字段，提示思考型模型预算不足
```

实测对比：

| | 修复前 | 修复后 |
|---|---|---|
| `/api/llm/test` 返回 | `reply: ""`（output 仅 8 token） | `reply: "可用"`（output 148 token） |
| 耗时 | — | 3.9s |

## 四、第二次发现：审查侧 token 预算不足

S4 单维审查首轮用 `max_tokens=2000`，结果 **产出 0 条 issue**：

```
维度=fact 规则=4 → issue=0 过滤=1  usage={'input': 471, 'output': 2000}   ← output 正好打满
```

`output` 精确打满 2000 = 输出被截断 → JSON 不完整 → 解析不出合法 issue。
把预算提到 **4096** 后立即恢复：

```
维度=fact 规则=4 → issue=2 过滤=0  usage={'input': 471, 'output': 2100}
    · [FACT-001] conf=0.8  截至 2024 年月活已经突破 10 亿。
    · [FACT-002] conf=0.9  截至 2024 年月活已经突破 10 亿。
```

> 结论：**思考型模型跑审查，`max_tokens` 建议 ≥ 4096**（= 思考链 ~525 + 思考链外的 JSON 正文余量）。
> `config/llm.local.json` 已据此调整为 4096。

## 五、全量审查实测结果

`review.run_one(target, rules, use_llm=True)` → **R-20261023-005**

| 指标 | 值 |
|---|---|
| 审查模式 | **`rule+llm`** ✅ |
| 裁定 | `fail` |
| LLM 调用次数 | **4**（fact / safety / style / compliance 各一次） |
| 失败次数 | **0** |
| Token 用量 | input 1786 / output 3084 |
| 端到端耗时 | 77.7s |
| 报告 issue 总数 | 3 |

### 逐维度明细

| 维度 | 候选 | 新增 | 与规则审重复 | 失败 |
|---|---|---|---|---|
| fact | 2 | **1** | 1 | 0 |
| safety | 0 | 0 | 0 | 0 |
| style | 0 | 0 | 0 | 0 |
| compliance | 1 | 0 | 1 | 0 |

### 链路有效性验证

- **LLM 真的被调用**：4 次调用、3084 output token、逐维度耗时均有记录（`logs/R-20261023-005/cost.json`）。
- **LLM 真的产生了价值**：fact 维新增 1 条规则审没抓到的 issue。
- **去重机制生效**：LLM 报的 FACT-001 / FACT-002 引用了同一句原文，其中 1 条被识别为与规则审重复而丢弃，避免同一句被报两次。
- **不可信输出被拦截**：LLM 只能提 `rule_id` + 逐字 `quote`，`quote` 必须在原文中逐字存在，校验不通过直接丢弃（`llm_review.validate`）。

## 六、给使用者的配置建议

| 模型类型 | 建议 `max_tokens` | 建议 `timeout` |
|---|---|---|
| 思考型（deepseek-r1 / qwen3 系） | **4096** | 180s |
| 非思考型（gpt-4o-mini / deepseek-chat） | 1024~2048 | 60s |

本地端点（`127.0.0.1` / `localhost`）**免 API Key** 即可用（`enabled: auto` 判定为 available）。

## 七、遗留与后续

1. **用户 8000 端口的控制台需重启**才能应用 `/api/llm/test` 的修复（当前进程仍是旧代码）。
2. `qwen3.5:9b` 在本次测评中作为备选未纳入正式跑批（思考链更长、单次延迟 6~16s，输出稳定性待观察）。
3. 建议把 `max_tokens` 下限校验与「思考型模型」场景关联（当前 `/api/llm/config` 只校验 16–8192 区间，不区分模型类型）。
4. 审查耗时主要来自本地推理（S5 中 4 次调用占 77.7s 的绝大部分），接入 GPU 更大的机器可显著加速。
