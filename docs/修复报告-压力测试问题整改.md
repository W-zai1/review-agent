## 二、逐项修复

### P1 类型误判：一次猜测改掉了整套判定标准

**问题**：`detect_type` 只要全文任意位置出现「合同/协议/甲方/乙方/签署/生效」任一关键词就判 `contract`。水段里一句「验收标准与合同附件一致」就让整篇会议纪要变成合同，连锁引发三件事：

1. 合同要件检查报出 3 条「缺甲方/缺争议条款」的**纯误报**；
2. 审查任务书 charter 变成「用途：合同 / 协议文本」，**每个维度的判定标准都被换掉**；
3. 数据披露检查（COMP-004）因类型不是文本类而被**关闭**——讽刺的是模型仍按同一 rule_id 报了 5 条，表面看"检查还在工作"，实际确定性检查已经停了。

**修复**：

- 标题/开头 600 字符加权：标题含「合同/协议」且开头 ≥2 个要件词，或开头 ≥4 个要件词，才判 contract；
- 引入**类型置信度**并写入报告 `coverage.type_detection`；
- **猜测只允许增加检查，不允许关闭检查**：类型置信度 <0.8 时不跑合同要件检查（避免误报），但**仍然跑** COMP-004；
- 人工 `--type` 覆盖时置信度记为 1.0。

**验证**：

| 样本 | 修复前 | 修复后 |
|---|---|---|
| 会议纪要（含"合同附件"字样） | contract（误判） | **llm_response / 0.85** |
| `contract_001.md` | contract | contract / **0.92** |
| `code_001.py` | code | code / 0.9 |

`stress_long_001.txt` 的 3 条 COMP 误报随之消失。

### P2 输入截断：不是"没渲染"，是数据链路断了

**问题**：`llm_review.review_dimension` 设置了 `truncated=True`，但 `review.py` **全篇没有一处读这个字段**——它只写进 `llm.dimensions[*].truncated`。于是 40,445 字的文档只审了前 12,000 字，而报告、limitations、coverage 全部没有任何提示。

**修复**（两层）：

1. **可见性**：新增 `coverage.chars_total / chars_reviewed / text_coverage_pct / complete`，并把「原文 X 字符，仅覆盖前 Y 字符（Z%），其后 N 字符完全未进入审查」**插到 limitations 第一位**（否则会被"事实库未命中"这类条目淹没）；结论正文也追加一句，Markdown 报告新增「文本覆盖」行；
2. **根治**：长文改为**分块送审**（见下文 P2+），不再截断。

---

### P2+ 长文覆盖：分块审查替代截断

**实现**：`review.plan_chunks()` 按段落边界切块（优先 `\n\n`，其次 `\n`，再退到句号），块间重叠 400 字符避免切断句子；每块单独送审，**quote 仍对完整原文校验**（块是原文子串，安全线不变）。

**配置**（`config/llm.yaml`）：

```yaml
max_input_chars: 12000   # 单次送审上限
chunking: true           # 长文分块（true = 不截断，成本换覆盖）
chunk_overlap: 400
chunk_chars: 6000        # 每块字符数
```

**为什么是 6,000 而不是 12,000**：实测 12k 的块单块发现就能写满 8,192 输出 token，`finish_reason=length` 再次出现；降到 6k 后输出截断维度从 3 个降到 1 个。块太小则调用次数暴涨，6k 是实测拐点。

**验证**（40,990 字干净样本）：

```
覆盖 40,990 / 40,990 字符（100%）· chunked=True · chunks=8
尾部 T1/T2/T3 全部命中（旧版位于 28,445 字符盲区，一条都看不到）
```

### P3 输出截断：判定条件几乎恒为假

**问题**：

```python
truncated_output = (not issues and not content.strip() and finish_reason == "length")
```

`_salvage_objects()` 一旦救回对象，`issues` 非空 → 条件**永远失效**。fact 维两次满载 8,192 token 都被判"正常"，`truncated_dimensions` 恒为空。

**修复**：条件收敛为唯一可靠信号 `finish_reason == "length"`，并区分两种后果：

- 一条都没救回 → 「该维度未完成审查，不能视为无问题」；
- 救回 N 条 → 「已救回 N 条完整对象，但排在后面的发现已丢失，结论不完整」。

**验证**：干净长文跑出 `output_truncated_dims: ['fact','logic']`，修复前恒为空。新增测试 `test_partially_salvaged_output_still_flagged` 专门锁住"救回对象也要标记"。

---

### P4 模型自否被当成结论

**问题**：`ISS-0015` 的 evidence 原文写着「……故本条不成立，撤回」，却以 `LOGIC-001 / major` 的身份进入待整改清单。模型自我纠错被当成了它的结论。

**修复**：识别 `撤回/不成立/无需整改/属误报/应予排除` 等表述，移入**第三态「已排除」**——既不进 `to_fix` 与统计，也不静默丢弃（"模型曾经怀疑过"本身是信息），报告新增 `excluded[]`，前端新增「已排除（模型自否）」区块。

**验证**：干净长文一次运行中分离出 **189 条自否**，全部没进清单；对抗样本中 E01 的伪造自否仍可正确排除。

---

### P5 配额按模型顺序硬截断

**问题**：`if len(issues) >= max_issues: break` —— 按模型输出顺序截断，且**不留任何记录**。长文里 minor 噪声会把 blocker/major 挤掉。

**修复**：

- 先收集全部候选，按 `严重度 → 置信度` 排序；
- **blocker/major 不占软配额**（只受 30 条硬上限约束），minor/nit 才取前 `max_issues_per_dim`；
- 每条被丢弃的候选都写入 `dropped` 原因（不再静默）。

**验证**：这正是 E06（样本代表性，major）与 E11（低温常识，major）从未命中的直接原因——它们以前被 minor 挤掉了，现在稳定命中。

### 额外 1：确定性算术层（新增 `tools/arith_check.py`）

稳定漏报的 6 条里 4 条是纯算术。搬到代码里，不调模型：

| 检查 | 依据 | 规则 | 置信度 |
|---|---|---|---|
| 分项加总 | 360+210+480=1050 vs 文中 1080 | LOGIC-001 | 0.95 |
| 日期-星期 | 2026-10-18 实为周日 vs「周六」 | LOGIC-002 | 0.97 |
| 起止日期 vs 历时 | 7/1→10/15 共 106 天 ≈3.5 月 vs「4.5 月」 | LOGIC-002 | 0.93 |
| 占比 vs 人数/总数 | 50/220=22.7% vs「25%」 | LOGIC-001 | 0.82 |
| 入职年份 vs 自述年限 | 2016 年社招 vs「十一年」 | LOGIC-007 | 0.75 |

**误报控制**：合计必须有「三项/四项」计数词；百分数不当金额求和；年份不确定就跳过星期检查；总人数不唯一就放弃占比；入职年份或第一人称自述不唯一就放弃工龄检查；容差覆盖四舍五入。

**验证**：自洽水段 23 处「三项合计」→ 22 处核对通过、1 处真错误命中，零误报；`issue.tool` 为 `arith_check:*`，可一眼看出不来自模型。

### 额外 2：同一句被两条事实断言各报一次

**问题**：`ISS-0001/0002` 同 rule、同 quote、只是依据不同（豆包 MAU vs 豆包推出时间），一句话在清单里出现两次。

**修复**：`Session.add_issue()` 按「同规则 + 同句（≥0.9 重合）」合并，依据拼接保留；规则层 11 处 append 全部改为走该方法。

---

### 额外 3：严重度与置信度脱钩

**问题**：干净长文里 117 条 major 中 **54 条置信度只有 0.6**（"百分比未标注口径"的启发式），把真错误埋了。

**修复**：`make_issue()` 中 `置信度 < 0.7` 时严重度降一级（blocker→major，major→minor），并在依据里注明「置信度 0.6 < 0.7，严重度已下调」。

---

### 额外 4：开放发现刷屏

**问题**：开放发现（`OPEN-*`）默认 severity 一律 `major`，长文单次运行刷出 **116 条 major**。

**修复**：默认降为 `minor`，仅 `置信度 ≥0.85` 才升 `major`；单次调用最多采纳 3 条（超出记入 `dropped`）。

**验证**：长文开放发现 116 → 18~28 条。

---

### 额外 5：长文清单被同类噪声淹没

**问题**：8 块 × 5 维的 minor/nit 累积后，清单里 300+ 条，人无法使用。

**修复**：`coverage.chunked=true` 时，同维度 minor/nit 只在清单展开前 8 条，其余折叠进 `suppressed`（**JSON 完整保留，未丢失**），并在 limitations 说明折叠数量。

---

### 额外 6：裁定语义超权

**问题**：`core_conclusion` 写「可放行，建议顺手处理 minor」，前端显示 `PASS`。

**修复**：删除「可放行」；前端 `PASS` → **「未发现 — 不等于通过」**；裁定横幅常驻「已审 X / Y 字符 (Z%)」，未全覆盖时黄色告警。

## 三、顺带查出：压力测试报告本身的两处错误

### 3.1 「mid 档全文可见仍漏 T1-T3」不成立

报告结论 4 称「mid 档全文可见仍漏 T1-T3，证明漏报源于跨段推理能力不足」。但**当前 `stress_mid_001.txt` 里没有 T1-T3**（`星火` / `11 月 5 日` / `售后` 命中数为 0），它们只存在于 `stress_long_001.txt`。

也就是说：mid 档"漏"是因为样本里没有，不是能力问题。报告称 mid 为 10,965 字，实际文件 11,082 字——**样本与报告不是同一版，结论无法复现**。

### 3.2 「自洽水段」其实不自洽

反查生成器 `tests/stress_gen.py`，发现三个缺陷：

| 缺陷 | 后果 |
|---|---|
| 费用率**写死**「约 15%」，按生成公式实际 22~23% | 每段水段自带算术错误 |
| 区域/部门/项目按 `i % len` **循环复用** | 同一部门同月出现两套数字 → 真实跨段矛盾 |
| 金额未 `round`（`12*2.1 = 25.200000000000003`） | 浮点尾数被模型报成 blocker |

**这是"长文异议暴涨"的主因**：模型报的很多"冲突"是**样本真的有冲突**，不是误报。样本层面污染了压力报告的全部 precision 结论。

**修复**：改写生成器——费用率由数据算出、主体加唯一编号、全部金额 `round`，并新增 `self_check()`：水段若出现任何算术发现 / 浮点尾数 / 主体重复，**直接拒绝生成**。

**验证**：重新生成后自检通过；`arith_check` 在 40,990 字长文上只命中 6 条**真错误**（E01/E03/E04/E08/T2/T3）。

**重新生成前后对比（同一引擎）**：

| 长文运行 | 异议数 | blocker | 说明 |
|---|---|---|---|
| 旧样本（水段不自洽） | 339 | 45 | 大量"冲突"确实是样本缺陷 |
| 新样本（自洽） | 161 | 12 | 剩余噪声来自模型判断，见第五节 |
