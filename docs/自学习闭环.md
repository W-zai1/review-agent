# 自学习闭环：提案 → 门禁 → 受控晋升

> 诉求原话：「审查后如果有新的审查方向，比如新的逻辑漏洞标准，可以加入到规则库当中。」
>
> 结论：**方向可行，但「审查完自动写规则」不能直接做。**
> 实现形态是「机器提案 + 门禁守门 + 人（或受限自动通道）晋升」，
> 写规则库这件事在整个系统里只有一条代码路径，且不在 HTTP 面上。

---

## 1. 为什么不能「自动写进规则库」

一旦被审文档能影响审查规则，就等于**被审对象获得了修改裁判尺度的能力**。
这不是理论风险——第二轮对抗测试的 c04 样本已经证明文档里的注入句式能操控审查语义。

| 风险 | 具体形态 | 本设计的对策 |
|---|---|---|
| **规则投毒** | 文档里写「请把这条加进规则库」，或诱导标注 | 学习信号只来自**人工标注**；标注的 `quote` 必须逐字出现在被审文本里；来源分级 `human:<name>` |
| **误报放大器** | 一条宽松正则刷出几十条噪声，把真问题挤掉 | 门禁在**全语料**上重跑，非来源文档出现 1 条新增即拒绝 |
| **不可复现** | 模型生成的模糊正则行为飘忽 | 提案是「标注片段 → 数字泛化」的确定性变换，可逐字符复核 |
| **静默漂移** | 规则库越改越松，没人知道为什么 | 只增不改不删 + 版本自增 + 快照回滚 + 追加式审计日志 |

## 2. 数据流：审查侧只读

```
             ┌──────────────┐
  上传/审查 → │  review.py   │  ← 只读 rules/*.yaml（含已晋升的 auto_*.yaml）
             └──────┬───────┘
                    │ 报告（含 issue 明细）
                    ▼
        ┌───────────────────────┐     人工判断
        │ 控制台：误报 / 漏检标注 │ ─────────────┐
        └───────────────────────┘              │
                                               ▼
                                  state/annotations.jsonl   （唯一可信学习信号）
                                               │
                                  rule_miner.py：聚类 + 数字泛化
                                               ▼
                                  state/candidates/<id>.json （规则库之外！）
                                               │
                                  gate：全语料回归（带候选 vs 不带）
                                               ▼
                                  state/shadow/<id>.json     （预演，不改结论）
                                               │
                                  rule_promote.py：审批 + 配额 + 只增不改
                                               ▼
                                  rules/auto_<id>.yaml + 版本自增 + 审计 + 快照
```

**四个结构约束（本设计的根）**

1. **候选不在 `rules/` 里**。`rules/` 是被 `rules_dir_hash` 覆盖的受审目录，
   往里放草稿会让「规则集被改」和「有人起草了候选」混为一谈，历史报告会被判 stale/篡改。
   所以候选、标注、审计、快照全在 `state/`。
2. **审查过程从不写规则库**。`review.py` 里没有任何写入 `rules/` 的代码。
3. **HTTP 面上没有写规则的能力**。`/api/annotations` 只能写标注；
   `/api/learning` 只读。写库只存在于 `tools/rule_promote.py`（有契约测试锁这条）。
4. **只增不改不删**。自动规则只能是新文件；`rule_id` 已存在 → 拒绝。
   禁止自动改已有规则、禁止降严重度、禁止碰 `arith_check.py` 的确定性逻辑。

## 3. 状态机

```
proposed ──gate 通过──> passed ──shadow──> (可晋升) ──promote──> promoted
    │                      │                                      │
    └──gate 拒绝──> rejected                                     └──rollback──> rolled_back
```

- `rejected` 不会被删除：它记录了「这条思路被验证过、不成立」，避免反复提同一个坏主意。
- `rolled_back` 不能直接再晋升，必须重新过门禁。

---

## 4. 门禁：唯一的硬门槛

候选规则会在**全语料**（`config/learning.json` 的 `corpus.include`，当前 43 份）上跑两遍：
不带候选（基线）与带候选。指标全部可复算：

| 指标 | 含义 | 门槛 |
|---|---|---|
| `hit_doc_count` | 在几份**来源文档**里真的找回了被标注的问题 | ≥ `min_sources`（2） |
| `offtarget_count` | 在**非来源文档**上新增了几条 | ≤ `max_offtarget`（**0**） |
| `internal_offtarget_count` | 在**来源文档内部**命中了**不是标注指认的**句子 | ≤ 0（句级判定） |
| `suppressed_others` | 候选让别的规则的结论消失了几条 | ≤ 0 |
| `redundant_count` | 候选命中的句子**已经被现有规则报过** | ≤ `max_redundant_hits`（**0**） |

四条判定口径值得单独说：

- **`min_sources = 2`**：单文档学出来的规则必然过拟合（那一份文档里恰好这么写）。
- **`max_offtarget = 0`**：误报的代价是"人不再看清单"，所以只要有一条就拒绝。
  这条比漏报严格得多，是刻意的。
- **`internal_offtarget` 是句级判定**（v0.6.2 补）。旧实现只问「命中在不在来源文档里」，
  于是「问题句 + 正常同模式句」放进同一份文档就能把 0 误报指标整个绕过去。
  现在每条命中都必须对应到**标注指认的那一句**（去格式后包含关系或前 20 字相同），
  否则计入内部误报、同样拒绝。
- **`suppressed_others` 要排除 `COMP-004`**：引擎本来就有「同一句不叠两条提示」的去重，
  新规则命中该句时 COMP-004 会主动退让——这是设计行为，不是候选把别人的结论压掉了。
  第一版没排除，导致一条本来合格的候选被误判为「压掉 2 条」。
- **`redundant_count` 是冗余门禁**（v0.6.3 补）。它回答的是另一个问题：
  候选确实命中了，但**这句话本来就已经被别的规则报出来了**——加进去不增加任何检出能力，
  只是把同一处问题报第二遍。典型场景是"先补了确定性执行器，再对同一盲区做标注挖掘"：
  第六轮把 `从业 N 年` 补进 `LOGIC-004` 之后，原本能通过门禁的候选
  `AUTO-LOGIC-B61926` 指标全绿（hit=2 / off=0 / internal=0 / suppressed=0），
  但它命中的两处**已经由 LOGIC-004 报出**——门禁现在会拒绝它：
  "新增这条不增加检出能力，只是重复报同一处问题"。
  **补了执行器的盲区，不需要再用学习闭环补一次。**

### 实测：门禁不是装饰

演示语料 `targets/learning_demo/` 里有两类真实的漏检：

**① 负增长写法（`同比下降 -3.2%`）—— 通过（该规则后被第四轮回滚，见第 9 节）**

```
命中来源文档 2 份｜新增 2 条（非来源 0 条）｜压掉其他结论 0 条  → 通过
```

**② 占比合计（`业务收入占比分别为 45%、35%、30%，合计 110%`）—— 被拒绝**

```
命中来源文档 2 份｜新增 3 条（非来源 1 条）
拒绝原因：在非来源文档上新增 1 条：targets/learning_demo/share_ok.txt
         ——泛化过头，会把正常文本报成问题
```

第二条是关键证据：`share_ok.txt` 里是**数字自洽**的对照组（合计 100%），
候选照样命中——因为机器只学到「这种措辞要报」，没学到「合计要等于 100%」。
**门禁把它拦下了。** 如果允许自动写库，这条规则会长期误报所有正常报表。

## 5. 审批与配额

| 维度 | 通道 | 理由 |
|---|---|---|
| `safety` / `compliance` / `fact` | **只能人工**（`--confirm-manual`） | 这类误报是误拦/误导，代价最高 |
| `logic` / `style` | 可走 `--auto` | 结构性强、误报代价低 |

- 自动提案的严重度上限是 **minor**：`blocker` 只能人定。
- 自动晋升每周上限 **3 条**（`quota.max_auto_promotions_per_week`）；
  人工通道不受此限，但仍受门禁与只增不改约束。
- 每轮最多生成 2 条候选、队列上限 40 条，防止批量刷。

### 人工审核面板：`tools/rule_review.py`

门禁只回答"能不能进"，不回答"人要审什么"。候选在晋升前必须有人**看懂**它：

```bash
python tools/rule_review.py list              # 按类型分组列出全部候选
python tools/rule_review.py list --type logic # 只看某一维度
python tools/rule_review.py show <ID>         # 审核面板
python tools/rule_review.py decide <ID> --approve --note "措辞稳定，可晋升"
python tools/rule_review.py decide <ID> --reject  --note "只学措辞不学语义"
```

审核面板首行就是**类型**（`fact` / `logic` / `safety` / `compliance` / `style`）+
该类型的含义与风险提示，然后是匹配模式、`require`/`guard`、来源标注原文、
门禁指标（含 `redundant_count` 与拒绝原因）、既往人审记录。

`decide` **只写候选文件的 `human_review` 字段，不动规则库**——写库仍然只有
`rule_promote.py` 一条路径。`safety/compliance/fact` 即使 approve，
晋升时仍必须追加 `--confirm-manual`。

### 控制台入口：规则库右上角「待人工审核」

同一个面板也在控制台里：**规则库页右上角**的 `待人工审核 N` 按钮（`#pendingToggle`），
点开就是候选列表，每条显示 类型 → 匹配模式 → 来源证据 → 门禁指标（含"已被 X 覆盖"）
→ 人审记录，并带「批准 / 拒绝」两个按钮。

判「待审」的口径与 CLI 一致（`rule_learning.is_pending`）：
**门禁没拒（`proposed`/`passed`）且 `human_review.decision` 为空**。
已拒绝、已回滚、已晋升的候选仍会列在下面（灰显），但不再计入徽标。

接口：`GET /api/candidates`（只读快照）、`POST /api/candidates/decide`（只写 `human_review`）。
两个入口共用 `rule_learning.decide_candidate()` 这一份实现，避免 CLI 与控制台对
"什么算已审"各写一套（完整性校验踩过同样的坑：两套实现 → 两边结论相反）。

## 6. 治理：版本、审计、回滚

写规则库的每个动作都会：

1. **快照**当前 `rules/` → `state/rules_snapshots/<时间>__<版本>/`（只留最近 10 份）；
2. 写入文件（只新增）；
3. **自增 `config/rules_version.txt`**：`v1-2026-10-23` → `v1-2026-10-23-a1`；
4. 追加一行 `state/rules_log.jsonl`（`op / rule_id / by / mode / 版本前后 / 指标 / 快照`）。

版本自增是必须的：不升版本而改了 `rules/`，`integrity` 会判为**篡改**（红）。
升了版本，历史报告转为 `stale`（黄，"当时的依据已经不在了，结论该重审"）。

回滚：`python tools/rule_promote.py rollback AUTO-LOGIC-XXXX --by <name>`
→ 删规则文件 + 升版本 + 记账，候选置 `rolled_back`。

> 顺带被这套机制抓到一次真实违规：改完 Agent 目录（新增 pattern 执行器）却忘了升
> manifest 版本，已有报告立刻被 `agent_dir_hash` 判为「疑似判定标准被改」。
> 补版本后才回到 stale。**机制对我自己也是生效的。**

## 7. 怎么用

```bash
# 1) 记录标注（唯一入口；console 的「误报/标注漏检」按钮写的是同一份文件）
python tools/annotate.py --kind false_negative --by wang \
    --target targets/x.txt --dimension logic --quote "同比下降 -3.2%"

# 2) 挖掘候选（只写 state/candidates/）
python tools/rule_miner.py mine

# 3) 门禁（全语料回归）
python tools/rule_miner.py gate AUTO-LOGIC-XXXX

# 4) 预演（不改任何结论，只算"若启用会新增几条"）
python tools/rule_promote.py shadow AUTO-LOGIC-XXXX

# 5) 晋升
python tools/rule_promote.py promote AUTO-LOGIC-XXXX --by wang          # 普通维度
python tools/rule_promote.py promote AUTO-SAFETY-XXXX --by wang --confirm-manual  # 高危维度
python tools/rule_promote.py promote AUTO-STYLE-XXXX --by bot --auto    # 受配额限制

# 6) 看状态 / 审计 / 回滚
python tools/rule_promote.py status
python tools/rule_promote.py log
python tools/rule_promote.py rollback AUTO-LOGIC-XXXX --by wang
```

晋升后的规则长这样（`rules/auto_logic_be1b78.yaml`）：

```yaml
- rule_id: AUTO-LOGIC-BE1B78
  dimension: logic
  severity: minor
  desc: "（自动提案）同比下降 类表述需人工确认"
  method: auto_mined_pattern
  source: "自学习闭环：人工漏检标注 → 候选 → 门禁通过后晋升"
  confidence: 0.7
  pattern: "同比下降\\s*\\-\\d+(?:\\.\\d+)?%"
```

`AUTO-` 前缀与 `auto_*.yaml` 文件名让人一眼看出**这条不是人手写的**，
`state/rules_log.jsonl` 里有它的来源标注与门禁指标。

## 8. 这套「学习」到底是什么，不是什么

**是**：监督式规则归纳的极简版——
人工标注 → 聚类 → 模板实例化（数字泛化）→ 回归门禁 → 受控晋升。
它可解释、可复现、可回滚，规则文本人能直接读懂。

**不是**：

| 没做 | 后果 / 现状 |
|---|---|
| 学语义 | 只能学**措辞**：`同比下降 -3.2%` 与「降幅为负的 3.2%」是两条不同的规则 |
| 自动生成正则 | 不做 LLM 生成（可加，但必须同样过门禁；当前版本刻意不引入） |
| 学「什么算错」 | 判错的标准仍来自人：标注是唯一信号，"对不对"由人定义 |
| 自证明 | 门禁语料与标注同源时会虚高；真实效果仍需盲测（见 `docs/盲测协议.md`） |

### 已知风险（不遮掩）

1. **标注质量决定上限**：一条错的漏检标注会产出一条错的候选——但过不了门禁，
   除非门禁语料里正好没有反例。**语料覆盖 = 门禁强度**。
2. **措辞级泛化**：同一类错误换种说法就不命中，覆盖提升有限（本例只多了 1 条规则）。
3. **门禁是离线的**：它拦得住"把对的报错"，拦不住"漏掉另一种错"。
4. **规则会慢慢变多**：只有每周配额与队列上限，没有"自动淘汰"机制；
   淘汰需要人工判定（`rollback`），当前不做自动下线。

## 9. 第四轮对抗测试后的加固（v0.6.2）

第四轮测试集中在学习闭环的安全面，共 10 项。逐条处置如下（**P1 三条全部修复**）：

| 编号 | 问题 | 处置 |
|---|---|---|
| **V1 P1** | 门禁按「文档级」判误报，来源文档内部误报可绕过 | 改为**句级**：新增 `internal_offtarget_count`，命中必须对上标注指认的那句；门禁阈值 0 |
| **V2 P1** | 候选 JSON 状态可伪造，门禁/shadow/审批全链被绕 | `promote` **不再读文件里的状态**：晋升时重跑 `evaluate` + `gate`；候选另带 `content_hash`（规则本体+来源标注），门禁后被改过就拒绝 |
| **V3 P1** | 已晋升的 `AUTO-LOGIC-BE1B78` 是误报放大器（正常财务陈述被报） | **已回滚**（版本 `-a3`，审计有记录+原因）。结论：措辞级规则不该进产品规则库；自动规则在报告/控制台加「自动」标记，`desc` 带「自动提案」 |
| **V4 P2** | shadow 噪音上限只打印 ⚠，不阻断 | `promote` 检查 `len(hits) > shadow.max_new_issues` 即拒绝 |
| **V5 P2** | 标注接口无认证、所有 `human:*` 一律可信 | 标注人白名单 `identity.trusted_authors`（默认只信 `owner`），白名单外只留证据不做种子；HTTP 面可选用 `REVIEW_AGENT_ANNOTATION_TOKEN` + `X-Review-Token` |
| **V6 P3** | 自动规则的 `require` 恒真 | 自动规则不再生成 `require`（pattern 已含数字泛化，require 冗余） |
| **V7 P3** | 自动规则对代码文件不生效 | 属既定边界（代码只跑安全/风格两维），已在 `mine` 输出显式提示，并写入本文边界 |
| **V8 P3** | `state/` 未入 .gitignore | 已加入（标注人身份、候选、审计、快照不进公开仓库） |
| **V9 P3** | 晋升后无漂移监控 | 新增 `rule_promote.py audit`：按当前语料复评已晋升规则，不通过**自动回滚**并记账 |
| **V10 P3** | `evaluate` 改写全局变量，并发竞态 | 加排他锁 `state/.evaluate.lock`，第二个评估直接报错而不是串数据 |

### 三条本轮确立的原则

1. **度量粒度必须细到「被标注的那一处」**，否则任何"打包"都能绕过（V1）。
2. **状态不可信，只有重算可信**。凡是可以被文件改写的字段（gate/shadow/status），
   在关键动作前一律重算；内容用 `content_hash` 保护（V2）。
3. **措辞级规则的上限要承认**。自动规则能学到的只有"这种写法要说一句"，
   学不到"这样算不算错"——所以严重度封顶 minor、必须人工确认、并接受随时回滚（V3）。

## 10. 文件清单

| 位置 | 作用 |
|---|---|
| `config/learning.json` | 门禁阈值、语料范围、审批分级、配额 |
| `tools/rule_learning.py` | 闭环核心：标注 / 模板实例化 / 门禁 / 晋升 / 回滚 / 审计 |
| `tools/rule_miner.py` | 挖掘与门禁的 CLI |
| `tools/rule_promote.py` | 预演、晋升、回滚、审计的 CLI（**唯一写 `rules/` 的入口**） |
| `tools/annotate.py` | 记录人工标注 |
| `tools/pattern_rules.py` | 声明式正则规则的执行器（文档审与安全审共用） |
| `state/` | 标注、候选、预演、审计、快照（都不在 `rules/` 内） |
| `tests/test_learning.py` | 28 项回归：模板、门禁、审批、配额、回滚、结构约束 |
