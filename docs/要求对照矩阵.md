# 要求对照矩阵（要求侧 vs 候选侧）

> 代码 `tools/match_matrix.py`　维度 `config/match_matrix.yaml`（v1-2026-10-26-a1）
> 接入点 `tools/purpose.py::analyze`（报告的 `purpose.matrix`）

## 1. 解决什么

目的文件（招聘 JD / 招标要求 / 客户检查清单）和待审对象（简历 / 投标文件）是**两份文本**。
在此之前，报告只能给出「哪些句子与目的相关」：

```
E1 support  「任职要求：本科及以上学历，熟悉 Python、SQL」
E4 support  「教育背景：某大学 硕士」「技能：python、Excel」
```

两条证据都在，但「学历这一项对上了没有」「要求的三项技能简历里有没有」仍然要人一行行比。
矩阵把这件事做成一张表：

| 维度 | 要求 | 候选 | 结论 |
|---|---|---|---|
| 学历 | 硕士 | 本科 | ❌ 不满足 |
| 经验年限 | 5 年 | 3 年 | ❌ 不满足 |
| 技能/工具 | Python、SQL、Excel、Tableau | Python、Excel | △ 部分未提及 |
| 薪资 | 提及「薪资」 | 期望薪资 | · 双方均提及 |

## 2. 谁能给结论（判定权限）

| 情形 | 结论 | 依据 |
|---|---|---|
| 两侧都能解析出**学历层级**或**年限数字** | `met` / `unmet` | 集合与算术比较，交代码 |
| 要求侧写了、候选侧字面没出现 | `absent` 未提及 | 「没写」≠「不具备」，不能判不满足 |
| 只有一侧能给结构化值 | `unclear` | 结构不够，交给人看 |
| 薪资 / 到岗这类区间与时点 | `mentioned` | 谁满足谁要谈，代码不下结论 |

**它不是判定，是对照表**：不产生 issue、不影响 verdict、不进 `stats`。
和 `tools/arith_check.py` 的分工一致——错的是「算」，不是「判」。

## 3. 抽取靠结构，不靠词表

| 维度 | 怎么认 | 刻意的取舍 |
|---|---|---|
| 学历 | 层级词 → 整数（博士 5 … 高中 1）。要求侧取**最低**层级（"本科及以上，硕士优先"不会把合格的人判成不满足），候选侧取**最高**学历 | 只认层级词，不猜"985/211" |
| 年限 | 只认「N 年…经验/经历」的显式写法 | **不按在职区间推算**：区间累计要拿"今天"当锚点，重跑报告会漂移，与「报告可复现」冲突。有区间无年限 → `unclear` 并说明原因 |
| 技能 | 引导词（熟悉/精通/掌握/技能…）之后、**同一小句内**的列举段，只收拉丁字母工具名 | 中文项**故意不收**：真实 JD 的「负责模型调用、检索」与「数据分析」在结构上无法区分，收进来就会报「未出现：调用失數」这种假缺口（OCR 噪声下实测踩到）。漏一项的代价远小于整张表失信 |
| 薪资 / 到岗 | 关键词出现即对照 | 只做「双方都写了」的提示；「可实习/实习期」不算到岗时点（那是岗位属性，会在实习生简历上稳定报噪声） |

要求侧**只来自目的文件**。手写目的（"帮我看看这合不合适"）是「要审什么」，不是「要求是什么」，
混进来会让矩阵把指令当要求。

## 4. 报告里在哪看

- JSON：`report.purpose.matrix`（`available / reason / dims[] / coverage / gaps[] / limitations[]`）
- Markdown：`## 审查目的与目标证据` → `### 要求对照矩阵`
- 控制台：审查目的卡片内的「要求对照矩阵」（满足绿、不满足红、未提及灰、无法判定紫）
- 任务日志：`S5.5` 步骤的「对照矩阵」一行摘要

没有生成矩阵时**不静默跳过**：报告会写 `> 未生成对照矩阵：<原因>`，
最常见的原因是「没上传要求侧文件」或「要求是散文式描述，没有可结构化项」。

## 5. 边界

1. 五类可比项之外（沟通能力、抗压、责任心）无法结构化，明确写进 limitations，不是漏了；
2. `absent` 只代表**字面未出现**；技能项还会额外声明「出现≠掌握、缺项≠不会」；
3. 方向固定：要求侧在**目的文件**里，候选侧是**待审对象**。反过来上传不会自动对调；
4. 新增维度只改 `config/match_matrix.yaml`，不用动 `tools/match_matrix.py` 的流程。

### 5.1 块标记（`【目的文件：名】`）怎么认

要求侧靠组装时写下的块标记切分。规则有四条，目的都是"块属于哪个文件"不模糊：

- **只认行首标记，且只有这一条路径**：真标记由 `server._assemble_purpose` 生成，独占一行
  （`【目的文件：名】\n正文`）。手写目的里出现的「请按【目的文件：JD】核对」在句子中间，
  不会被当成块起点（全文搜索会把它当起点，于是要求侧变成"句子后半截"，矩阵跟着错）。
  没有行首标记 = 没有要求文件，如实报"未生成矩阵"，**不编块**：
  曾经的回退分支会用 `[^】]+` 跨行取名，把下一行正文当文件名
  （`"【目的文件：\n核对学历】看这里"` → `name="核对学历"`），已删除。
- **名字取该行最后一个 `】`**：文件名自带 `】`（`JD【1】.txt`）不会被截断成 `JD【1`。
  上传侧再加一道：名字里的 `【】《》（）` 写进块标记时改写为 `[ ] < > ( )`
  并在返回 warnings 与报告说明里写明，暂存列表仍保留原始文件名。
- **说明尾巴按固定措辞剥离**：组装会在末尾追加「（说明：…）」（截断 / 改写名字），
  它属于元信息，不能混进要求侧正文；但只认 server 生成的那几种固定开头，
  正文里自然写的「（说明：…）」原样保留。
- **入口规范化**：`\r\n`/`\r` 一律转 `\n`（`\r` 是隐形字符，按 `$` 匹配的正则会被它挡掉）；
  空名字归一为「未命名」，与上传侧同措辞。

仍未解决：正文自己有一行以「【目的文件：」开头时，与真块在语法上无法区分，
会被切成两块（`tests/bruteforce_matrix.py` 的 A6、v2 的「手写段伪标记」记为已知边界）。
根治要给块加不可伪造的结束标记，属于格式变更。

## 6. 测试锁了什么

`tests/test_match_matrix.py`（33 项）：

- 没有目的文件 → 不生成矩阵，且给出原因；手写目的里的"硕士"不会被当成要求；
- 学历：高于要求 `met`、低于 `unmet`、未提 `absent`、"硕士优先 + 本科及以上"取最低层级；
- 年限：`met`/`unmet`、"2021.07-至今"只能是 `unclear`（不自行推算）、"2021年3月"不算 3 年经验；
- 技能：大小写不敏感、中文动词短语不收、「业务流程」这类修饰语不收、下一个引导词处截断；
- 措辞：`absent` 行不得出现「不具备」「不会」；
- 安全性：同输入同输出、加不加 issues 矩阵不变、坏正则/缺配置不抛异常；
- 渲染：markdown 有矩阵表与技能逐项；没有矩阵时有原因；
- 块标记：手写目的里的 inline 提及不切块、名字自带 `】` 不截断、
  畸形标记（标记行无 `】`）不拿下一行正文造块、空名归一为「未命名」、CRLF 规范化；
- 前端契约：`MX_CN` 与后端 `STATUS_CN` 键集合一致、矩阵容器样式存在。

另有 `tests/test_api_contract.py::PurposeUploadTests::test_matrix_generated_when_requirement_file_uploaded`
做端到端验证（上传要求文件 → 报告里有矩阵 → verdict 不被改坏），
`test_purpose_marker_sanitized_for_delimiter_name` 验证含 `【】` 的文件名
"上传即提示 / 暂存保留原名 / 块标记用安全名并在报告里写明"。

```bash
python -m unittest tests.test_match_matrix -v
python -m unittest tests.test_api_contract.PurposeUploadTests -v
```
