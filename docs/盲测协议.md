# 盲测协议 · 用真实文档校准召回率

**为什么需要这份协议**：目前的 100% 召回是在"我们自己出的考卷"上拿到的——
样本是生成的、错误清单是列的、标签是写的、修复也是同一批人做的。
它只证明"能命中我们设计的错"，不能证明"能命中真实文档里的错"。

真实召回必须用**没被我们设计过**的文档测。流程如下。

## 一、准备文档（3–5 份）

建议覆盖真实业务里最常被审的形态：

| 类型 | 建议 |
|---|---|
| 合同 / 协议 | 至少 2 份，含 1 份条款不全的（能测要件检查） |
| 会议纪要 / 汇报 | 至少 1 份，含跨段数字矛盾（能测逻辑维） |
| 对外宣传稿 / 公告 | 1 份（能测合规与事实维） |

放进 `targets/`，例如 `targets/real_contract_01.md`。

## 二、先标盲，再看模型（关键）

```bash
# 1. 生成空白标注模板（不跑审查，避免被模型输出带偏）
python tools/eval_review.py --sample targets/real_contract_01.md --init-labels 12
```

生成 `targets/real_contract_01.labels.json`，你需要填每条：

```json
{
  "id": "B01",
  "desc": "第三条违约金比例 30% 超过法定上限",
  "match": [["违约金"], ["30%|上限|过高"]],
  "exclude_dimensions": ["style"]
}
```

`match` 是 **AND-of-OR** 结构：每个子数组里任一正则命中即可，所有子数组都要命中。
匹配文本 = `quote + evidence + suggestion + rule_text`。编写原则：

- 只用**判定依据**里的词，不要用你可能想象的措辞；
- 同一错误的不同说法用 `|` 并列（例：`"30%|三成|上限"`）；
- `exclude_dimensions: ["style"]` 必须保留——风格规则会整句引用问题句，
  不排除会让召回虚高（实测 8/14 → 7/14）。

**标注时不要打开任何报告或模型输出。** 这一步的价值全在独立性。

## 三、跑评测

```bash
python tools/eval_review.py --sample targets/real_contract_01.md --runs 3
```

看三件事，而不是只看召回：

1. **召回**：`命中标注数 / 标注总数`；
2. **标注命中率**：你的清单里有多少条能对上标注（其余需人工裁定是噪声还是漏标）；
3. **稳定命中 / 时有时无 / 从未命中**：`从未命中` 才是真能力缺口，
   `时有时无` 说明该能力靠运气。

## 四、怎么解读结果

| 结果 | 结论 |
|---|---|
| 召回 ≥80% 且 3 次稳定 | 可以作为可靠辅助工具 |
| 召回 50–80%，有 `时有时无` | 只能当"提示器"，不能当门禁 |
| 召回 <50% | 定位问题在规则/提示词，而非模型不够强 |

## 五、注意事项

- **不要用同一份文档既调参又报成绩**：看完结果改 prompt 再测同一份，就是过拟合。
  要么留一份"测试集"不碰，要么每次换新文档。
- 真实文档往往含隐私，`targets/` 与 `outputs/` 都在本机，
  但报告里会存原文快照（`target_text`），外发前注意脱敏。
- 标注本身有主观性：同一份文档两个人标，条数可能差 20%，这属正常，
  重要的是**先定口径再标**（例如"口径缺失"算不算错误）。

## 六、冻结 holdout + 命令 + 结果解读

上面第一至五节是**探索性盲测**（3–5 份，适合发现问题和积累标注口径）。
要对外报「真实召回」，必须用本节的 **holdout 验收**：30–50 份独立文档、
冻结清单、固定命令、置信区间。完整操作手册见
[holdout/README.md](../holdout/README.md)，实现见
[tools/holdout_eval.py](../tools/holdout_eval.py)。

### 1. 放文档与盲标

- 文档放 `holdout/cases/<name>.txt`；
- 标注放 `holdout/labels/<name>.labels.json`（格式与 `tests/golden/labels/` 一致）；
- 没有 label 的 case 是干净对照，期望 0 issue；
- 先人工通读、独立写完 label，**再看模型输出**。不要拿 `tests/golden/` 或
  `targets/` 里的文档充数。

### 2. 冻结

```bash
python tools/holdout_eval.py --save-manifest
```

生成 `holdout/MANIFEST.json`，记录每份 case/label 的 sha256 与 `frozen_at`。
冻结后改任何一个字节（包括换行、编码），评测器都会拒绝出分。清单已存在时
默认拒绝覆盖；重冻结必须显式 `--save-manifest --force`，且旧成绩作废。

### 3. 跑验收

```bash
# 只测，不设门槛
python tools/holdout_eval.py

# 正式验收：低于门槛退出 1
python tools/holdout_eval.py --min-recall 0.80 --min-precision 0.90

# 结果默认写 outputs/holdout/holdout-<timestamp>.json
python tools/holdout_eval.py --json outputs/holdout/release-0.9.1.json
```

- 纯规则审查（`use_llm=False`），不联网、不调 LLM，可复现；
- 复用 `tools/eval_review.py` 的 `run_once`，其临时目录隔离不会写正式报告；
- 评测前后各校验一次 manifest，评测期间文件被改也退出 2。

退出码：`0` 达标；`1` 评测完成但低于门槛；`2` 无法评测（空 holdout、
清单缺失/损坏、文件增删、hash 变化、标注非法）。空目录时**不会**静默给 0 分。

### 4. 结果解读

- **recall** = 命中标注数 / 标注总数；
- **precision** = 命中标注数 /（命中标注数 + 标注外 issue 数）；
- 两者都带 **Wilson 95% 置信区间**；分母为 0 时显示 `n/a` 并记 `[0, 0]`，
  不要读成 0%；门槛判断时该比例按 0 处理（没有证据不算达标）；
- 看**区间下限**，不要只看点估计：例如 60 条命中 48 是 80.0%，但 95% CI
  约 `[68.2%, 88.2%]`，不能据此断言真实召回一定 ≥80%；
- 只有 5–10 份文档时区间极宽，只能当探索结果；30–50 份才谈得上验收；
- 看到漏检先记录，不要回头改规则再跑同一份 holdout。要验证修复，用新文档
  或等下一轮 holdout。

CI/门禁可以这样接（失败即阻断发布）：

```bash
python tools/holdout_eval.py --min-recall 0.80 --min-precision 0.90
```

### 5. 红线

holdout 只用于验收，不参与调参。拿它的结果改 prompt/规则、再用同一份 holdout
复测，等于把考卷提前发给考生；连续几轮后，它就和 `tests/golden/` 一样只证明
「能命中我们设计过的错」。
